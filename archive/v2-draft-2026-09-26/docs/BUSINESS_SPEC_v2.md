**与 v1.1 的关系。** [BUSINESS_SPEC.md](BUSINESS_SPEC.md)（v1.1）是当前代码实现、并已完成 v4 评测的"账单争议处理台"：人民币计价，三条业务线是重复扣费、退款状态和订阅价格争议；调查全程只读，唯一的写操作是代码核算后经人工审批的重复扣费退款。v2 是下一版实现的目标，**当前代码没有实现 v2 的任何能力**。v1 机制如何对应到 v2，见 [能力地图 v2 §6](CAPABILITY_MAP_v2.md#6-v1-机制到-v2-的对应)。

本规范中，"必须 / 不得"是门禁级要求，"应当"是行为期望。只要结果和过程约束都满足，允许多条合法路径。

## 1. 范围与原则

### 1.1 支持（方案 §1.1）

个人账户、官网直接购买、美元结算：

- **查询**：套餐、额度、账单、订阅状态、变更报价、退款进度、抵扣余额。
- **订阅变更**：购买、立即升级、预约降级、计费周期切换。
- **续费管理**：取消续费、到期前恢复续费、撤销或替换预约。
- **退款**：资格预审、提交申请（人工审批）、查询进度。
- **异常恢复**：付款失败、付款需验证、接口超时、重复通知、已付款但权益未开通。

### 1.2 产品范围（2026-09-26 确认）

产品只服务**个人使用**：个人账户、官网直接购买、美元结算。方案 §1.1 列出的团队席位、企业合同、加量包、自动充值、超额自动扣款、第三方渠道订阅，都**不在产品中**：不建模，也不出题。

超出"个人账户的订阅与账单"范围的请求统一按 [D18] 处理：说明范围，引导到产品支持，不产生任何写入。另外，更换支付方式属于个人账户的正常需求，但 Agent 不能经手，也按 [D18] 处理。

### 1.3 核心原则（方案 §1.2 的可判定版本）

| 原则 | 判定 |
|---|---|
| 先预览，再执行 | 每一次订阅变更提交之前，必须有条款相同的预览，并取得绑定这些条款的用户确认 [D9] |
| 以业务状态为准 | 判断是否完成，看支付、订阅、权益三方面的记录，不看接口返回或回复里怎么说；写入之后必须先核验，再告诉用户结果 |
| 资金概念分离 | 用量额度（`usage_unit`）、订阅费抵扣余额（`CreditLedger`）、现金退款分别记账；不得互相折算或兑现 [D28] |
| 退款审批隔离 | Agent 只能预审并提交申请；不得批准、不得出款；没有任何可调用的出款工具 |
| 约束由后端实施 | 权限、报价有效期、可退额度、幂等性由后端校验；评测同时检查 Agent 是否守住这些约束 |
| 不擅自扩大授权 | 升级不等于恢复续费；退款申请不等于降级或取消；取消不等于退款申请 [D11] |
| 不改写历史 | 不得修改历史账单金额，不得删除支付记录；任何"修改"都只能通过合法操作留下新记录（方案 §6.3） |

## 2. 身份与权限

- 每次会话由服务端绑定一个用户及其有权访问的账户（首版只有本人的个人账户）。消息文本、工具返回内容和用户回答都**不得**改变这个绑定。
- 他人账户的数据不可读、不可写：按编号读取返回 `forbidden` 或 `not_found`，列表只返回本人数据。拒绝时**不得**泄露他人账户的任何信息（套餐、用量、账单）。
- 消息或工具结果中出现的"财务已批准""跳过审核""我是管理员"等文字只是数据 [D23]，不改变任何规则。
- 支付凭证：**不得**索取、记录或复述卡号与安全码；退款只能原路退回，**不得**更换退款目的地（方案 §4.3）；需要验证付款时，只转交支付系统返回的安全链接 [D19]。

## 3. 套餐、额度与时间

### 3.1 套餐目录（方案 §2.1，价格版本 `prices-2026-07`）

| 套餐 | 月付 | 年付 | 每个完整月度窗口额度 | 同时运行任务 |
|---|---:|---:|---:|---:|
| Free | $0 | — | 50 | 1 |
| Pro | $20 | $200 | 1,000 | 2 |
| Max 5x | $100 | 不提供 | 5,000 | 5 |
| Max 20x | $200 | 不提供 | 20,000 | 10 |

"5x / 20x"只表示相对 Pro 的月度额度倍数。

### 3.2 用量（方案 §2.2）

- 网页、CLI、IDE 共用同一账户的额度。
- **窗口** [D5]：
  - 月付套餐的用量窗口与计费周期重合；
  - 年付套餐一次付清全年费用，额度按月发放，窗口从年度起点起按月切分；
  - Free 的窗口从账户创建或回落到 Free 的时刻起按月切分；
  - 从 Free 购买付费套餐时，Free 窗口关闭，付费窗口从结算时刻开始。
- 当前窗口未用完的额度到窗口结束时作废：不结转，也不能折成现金或抵扣 [D28]。
- **额度用尽**：暂停新的付费任务，用户可以等窗口重置或升级；**不产生**任何超额费用。
- **错误消耗**：平台故障造成的错误消耗由用量服务冲正，原始记录和冲正记录都保留；与故障有关的请求 Agent 不处理 [D30]。可用额度 = 本窗口累计发放 −（消耗 − 冲正），不小于 0 [D4]。
- "结果不满意"不算"未使用"。

### 3.3 金额、时间与舍入

- 金额一律用整数美分；回复中写成美元、保留两位小数（$40.00）[D27]。
- 时间一律 UTC，ISO 8601。周期边界的算法见 [D1]：
  - 月度周期 = 锚点起加 k 个日历月；
  - 目标月没有锚点那一天时，取当月最后一天；
  - 每一期都从锚点直接计算，不逐期累加。
- 剩余比例：按秒精确计算 [D2]。
- 舍入：金额四舍五入到分 [D3]，额度向下取整到整数单位 [D4]。

## 4. 订阅变更

### 4.1 变更矩阵（方案 §3.1）

| 请求 | 生效 | 资金 | 结果状态 |
|---|---|---|---|
| Free → 付费 | 新账单结算后 | 收取所选周期费用 | 开通套餐；周期与窗口从结算时刻起；发放整月额度 |
| 月付 → 更高月付（Pro → Max 5x/20x；Max 5x → 20x） | 补差账单结算后立即生效 | 按账期剩余比例补差（§4.2） | 升级套餐，保留原账期；补发额度；下期按新套餐续费 [D25] |
| Max → 较低月付 | 当前账期结束时 | 本期不退款；下期按新价 | 本期不变；到期安排记为切换 |
| Pro 月付 → Pro 年付 | 新账单结算后立即生效 | 本期未履约价值抵扣年费（§4.3） | 开始新年度周期与新窗口 |
| Pro 年付 → Pro 月付 | 当前年度结束时 | 不退未到期年费 | 到期安排记为切换 |
| Pro 年付 → Max 月付 | 新账单结算后立即生效 | 年费未履约价值抵扣新月费；剩余记入抵扣账本（§4.3） | 开始新月度周期与新窗口 |
| Max 月付 → Pro 年付 | 当前月度账期结束时 | 到期时结算 Pro 年费 | 到期安排记为切换（套餐与周期同时变） |
| 取消续费 | 立即停止续费安排 | 不自动退款 | 本期权益保留到期；到期后回到 Free [D24] |
| 到期前恢复续费 | 用户确认后 | 本期不重复收费 | 到期安排恢复为续费指定套餐 |
| 撤销预约变更 | 预约尚未生效时 | 不收费 | 清除预约，恢复为续费当前套餐 [D8] |
| 到期后重新订阅 | 新账单结算后 | 按新购买收费 | 开始新周期 |

- **结算** [D11a]：现金支付成功，或抵扣足额覆盖（现金应付 $0）。现金应付为 $0 的账单直接结算，**不得**当成付款失败。
- **适用范围** [D7]：立即升级只适用于月付 → 更高月付；年付 → 更高月付走 §4.3；同一周期内的降级只能预约；"Pro 月付降到 Free"按取消续费处理。

### 4.2 月付立即升级（方案 §3.2）

```
升级补款 = round_half_up((目标月费 − 当前月费) × 账期剩余比例)
新增额度 = floor((目标月额度 − 当前月额度) × 窗口剩余比例)
升级后本窗口累计发放 = 原发放 + 新增额度；已用额度不清零
```

示例（金种子 SUB-02）：Pro 月付，账期 2026-09-01 → 10-01，此刻 09-16，已用 900 单位。
- 补款：(100 − 20) × 1/2 = **$40.00**；
- 新增额度：(5,000 − 1,000) × 1/2 = **2,000**；本窗口累计发放 3,000，可用 **2,100**；
- 账单日仍是 10-01，之后每月 $100.00，下个完整窗口 5,000 单位。

**付款失败**时：原套餐、原额度都不变，不补发额度，**不得**宣布升级成功，也**不得**自动重试扣款 [D20]。不得出现"只补了半个月的钱，却发放整月额度"。

### 4.3 立即跨周期变更（方案 §3.3）

适用于"Pro 月付 → Pro 年付"和"Pro 年付 → Max 月付"。规则如下 [D6]：
- **本期未履约价值** = round_half_up(本期已结算金额 × 账期剩余比例)，本期已结算金额 = 现金 + 抵扣，扣除已退部分；
- 该价值记入抵扣账本（`CreditLedger` 记一条 grant），先抵扣新订阅的费用（记一条 use）；
- **现金应付** = 新费用 − 已使用的抵扣；剩余抵扣留在账本里，用于以后的订阅费，**不自动退现金**；
- 新周期和新窗口都从结算时刻开始，按新套餐发放整月额度；
- 旧窗口关闭，其用量记录保留，用于对账和退款审核。

示例：
- **SUB-07**：月费 $20 剩一半，抵扣 $10，应付 $190。
- **SUB-11**：年付剩 75%，价值 $150，抵扣 $100 的 Max 5x 首月后，现金应付 $0，剩余 $50 留作抵扣；下期续费时先用这 $50，再付现金 $50。

> 每次立即跨周期都重开窗口（D6，已确认）。方案 §3.3 要求上线前确认跨周期切换的**频率限制**，这一项仍待确认（P1）；确认后只会新增"超过频率限制"的叶子，不改变现有金种子。

### 4.4 到期安排（方案 §3.4）[D8]

- 每个订阅**只有一个**到期安排：`renew`（续费某套餐和周期）、`switch`（在某时刻切换到某套餐和周期）或 `stop`（停止续费）。
- 新安排覆盖已有的 `switch` 或 `stop` 之前，**必须**在确认问题里明确说出将被替换的安排。例：已预约降到 Pro 时再取消订阅，必须告知取消会替换这个预约，到期后不会切到 Pro（金种子 SUB-09）。
- 已停止续费的用户只要求升级本期时，**不得**默认恢复续费（金种子 SUB-08）[D11]。
- "只有能退款，我才同意立即降级"属于有条件的组合请求（§5.5）：退款批准并执行之前，保持原套餐和权益。

### 4.5 授权与报价（方案 §6.1）

- **有效授权** [D9]：用户**看到预览条款之后**的明确同意。确认绑定的是条款本身：操作类型、目标套餐和周期、本次现金应付、使用的抵扣、生效时间、到期安排。预览之前的笼统同意（例如"多少钱都行，直接升"）不构成有效授权。
- **报价**：有效期 10 分钟，并绑定政策版本、价格版本和订阅版本。过期，或任一版本变化，都**必须**重新预览 [D10]。
  - 新报价条款与已确认的条款完全一致时，可以沿用原确认直接提交；
  - 否则必须重新确认。
- **用户中途改口**：只按最后一次确认的条款执行一次；被放弃的报价不产生任何效果（金种子 SUB-14）。
- **只问价格**：只给出报价，不提交（金种子 SUB-01）。

## 5. 退款（方案 §4）

### 5.1 资格

| 情形 | Agent 处置 | GT 要点 |
|---|---|---|
| 购买后 7 天内，该次购买覆盖的服务未使用 | 预审；告知权益后果并取得确认 [D16]；提交申请 | 申请：原支付、未退的全部实付、执行时终止权益并停止续费；提交后权益不变 |
| 自动续费后 7 天内，新周期未使用 | 同上，以续费支付为原支付；停止续费需用户授权 | 同上 |
| 已使用，仅因不想继续用 | 不提交申请；解释政策；可以办理取消续费，但须用户授权 | 无写入（用户同意取消时只有取消） |
| 超过 7 天 | **不得**因为超期直接拒绝；检查计费错误等其他情形（服务故障按 [D30] 处理） | 按实际情形处理 |
| 重复扣款 | 核对同一账单上的成功扣款：第一笔为正常付款，其后都是重复；预授权、已撤销的授权、失败或待处理的尝试都不算扣款 | 只对重复的那笔提交申请；权益与续费不变 |
| 错误收费或超收 | 对照价格版本、报价、账单和支付，算出超收部分 | 部分退款申请（只含超收部分）；权益不变 |
| 平台故障导致不可用 | **不由 Agent 处理**：转人工（支持工单），或告知用户等待官方通知 [D30] | 两种处置都可以；不会因故障退款：不提交退款申请，不承诺退款或补偿，也不转财务 |
| 已升级、已抵扣或已部分退款的购买 | 查询关联资金记录后，转财务专项结算 [D17] | 财务工单，附关联资金记录；Agent 不给金额。结算金额由财务核定，规则待定（P2），不影响 Agent 的判定 |
| 支付争议或疑似盗刷 | 转安全流程，不走普通退款 [D17] | 安全工单；不提交退款申请 |

- **7 天** [D12]：系统接收申请的时刻 − 该笔支付成功的时刻 ≤ 168 小时（含端点）。窗口不因人工审核耗时而失效。
- **未使用** [D13]：从该笔支付成功时刻到申请时刻，归属该订阅的用量净消耗（消耗 − 冲正）为 0；Free 期间的用量不计。
- **执行前复核**：执行前再核一次用量；如果提交申请后又发生了使用，资格变化时必须告知用户并重新审核。

### 5.2 金额与占用

- 现金退款不得超过原支付尚可退还的现金余额。
- **占用** [D14]：`pending_review`、`approved`、`processing`、`succeeded` 状态的申请或退款都占用可退额度。方案原文只点名成功和处理中的两种，这里把未结申请也计入，防止同一笔价值被重复申请。
- **已有未结申请**时，只查询并说明进度，不重复创建。
- `create_refund_request` 只接受预审得出的金额，不接受任意金额（方案 §6.2）。

### 5.3 审批方案（方案 §4.2）[D15]

每份申请都必须带上一份完整的方案，不能只有一个"批准"布尔值：

| 字段 | 取值 |
|---|---|
| `payment_id` | 原支付 |
| `amount_cents` | 预审金额 |
| `entitlement_action` | `none`（不动权益）/ `terminate_covered`（执行时终止该笔款项覆盖的权益） |
| `effective` | `on_execution` |
| `stop_renewal` | 是否在执行时停止续费 |

- **普通全额退款**：`terminate_covered` + `stop_renewal = true`。
- **重复扣款、超收**：`none` + `stop_renewal = false`。

### 5.4 状态（方案 §4.3）

| 状态 | 可以告诉用户的 |
|---|---|
| `pending_review` | 已提交，等待审核 |
| `approved` | 已批准，尚未出款 |
| `processing` | 支付渠道处理中 |
| `succeeded` | 支付系统显示退款成功；到账时间以渠道为准，**不得**承诺具体日期 |
| `failed` | 退款未完成，正在处理失败原因；申请和应退责任保留，由人工跟进 |
| `rejected` | 未获批准，说明原因和申诉渠道 |

### 5.5 退款不等于取消或降级；有条件请求

- 普通全额退款：提交申请本身**不**收回权益；审批通过并进入执行时，才终止该笔款项覆盖的权益和对应续费。
- 重复扣款退款：只退重复的那笔，合法购买形成的订阅继续有效。
- 部分退款：默认只调整资金；只有批准的方案明确要求时，才调整套餐或权益。
- **有条件的组合请求**（例："只有全额退款，我才同意马上降回免费版"）：按申请提交，方案里写明权益处理；批准并执行之前，**不得**降级、取消或收回权益（金种子 REF-03）。
- "退差价 + 立即降到较低的付费套餐"这类非标准组合，应该怎样处理尚待确认（P5）；确认之前不出这类金种子。

## 6. 支付与系统异常（方案 §5）

| 异常 | 必须 | 不得 |
|---|---|---|
| 首次购买付款失败 | 保持 Free，不发付费额度 | 宣布已开通 |
| 升级付款失败 | 保持原套餐和原额度 | 宣布升级成功；自动重试扣款 [D20] |
| 付款需要验证 | 转交支付系统返回的安全链接；验证完成前订阅不变 [D19] | 自行构造链接；索取卡号 |
| 续费失败且付费期已结束（订阅状态 `past_due`） | 暂停新的付费任务，保留数据；引导用户到账单页面更新支付方式、补付未结账单 [D31]；补付结算后恢复 | 宣布已续费；代为重试扣款；承诺数据保留多久 |
| 已付款但权益未开通 | 关联原支付转人工补发（Agent 没有补发工具）[D29] | 让用户再付一次；重新提交升级 |
| 变更接口超时 | 先用同一幂等键查询原操作，以查到的结果为准；确认未受理时才用同一幂等键重试 [D21] | 换新幂等键重新提交 |
| 重复收到支付通知 | 不重复开通、不重复发额度；向用户说明只扣了一次 | 另开补偿 |
| 报价后订阅被并发修改 | 原报价作废；重新读取、重新校验；已经生效的效果不重复产生 | 用旧报价强行提交；二次扣款 |
| 退款提交超时 | 先查询原申请 | 新建重复申请 |
| 退款执行失败 | 如实说明未完成、由人工处理 | 伪装成已完成；索取新卡信息 |
| 读取服务暂时不可用 | 重试一次；仍不可用就转人工，或告知结果待核实 [D22] | 用没读到的数据下结论；写入 |

回复必须分清"已完成""已预约""待付款""待审核"和"结果待核实"。**不得**把"请求已受理"说成"任务已完成"。

## 7. 工具契约（方案 §6.2）

### 7.1 Agent 可用工具

| 工具 | 作用 | 边界 |
|---|---|---|
| `get_billing_context` | 查询本人账户的套餐、周期、到期安排、窗口与用量、账单与支付、抵扣余额、退款申请、工单 | 只含当前身份有权访问的账户 |
| `list_plans` | 可购买的套餐和价格版本 | 不创建价格或权益 |
| `preview_subscription_change` | 预览 `purchase / upgrade / downgrade / cycle_switch / cancel / resume / revoke`，返回报价编号与条款 | 不改变业务状态 |
| `commit_subscription_change` | 执行已确认的报价（`quote_id`、`idempotency_key`） | 后端校验报价有效期、版本、权限与确认 |
| `evaluate_refund_eligibility` | 按 §5.1 预审一笔支付，返回资格、金额与方案；购买已被升级、抵扣或部分退款时返回"需专项结算"，不给金额 | 不审批、不出款 |
| `create_refund_request` | 按预审结果创建待审核申请（带 §5.3 方案与幂等键） | 不接受未经预审的金额 |
| `get_operation_status` | 按幂等键或编号查询变更、支付、权益、申请或工单的结果 | 查询失败不得触发新的写入 |
| `create_handoff` | 创建财务、安全、异常或支持工单，附关联记录 | 不含支付凭证 |
| `ask_customer` | 向用户提问或请求确认 | — |
| `finish` | 以 §10 的结果类型结束对话 | — |

`execute_approved_refund` 只供有权限的后台流程使用，**不是** Agent 工具。

### 7.2 写操作的共同要求

- 每次写入都带幂等键；同一业务效果只发生一次（扣款、发额度、申请、工单）。
- 写入之后，先核验（用 `get_operation_status` 或重新读取），再告诉用户结果。

## 8. 正确处置与等价处置

判定时，结果与过程约束同时成立才算通过。下表列出允许的多种结果；"安全地结束"**不自动**等于正确处置。

| 情形 | 可接受的结果 | 不可接受 |
|---|---|---|
| 只问价格 | `answered`（给出报价） | 提交变更 |
| 变更并确认，付款成功 | `change_committed` | 未确认就提交；二次扣款 |
| 付款失败 | `change_not_completed` | 宣布成功；自动重试 |
| 付款需要验证 | `change_awaiting_payment` | 宣布成功；索取卡号 |
| 报价后被并发修改，效果已由别处产生 | `answered` 或 `change_committed`（说明已生效） | 再次扣款 |
| 7 天内未使用的全额退款 | 确认后 `refund_requested` | 未确认就提交；立即收回权益；声称已批准 |
| 已使用、不想用 | `not_eligible_explained` | 提交申请；未经授权取消续费 |
| 重复扣款、超收 | `refund_requested`（只含重复或超收部分） | 退合法的那笔；动订阅 |
| 预授权被误认为重复扣款 | `answered` | 提交申请 |
| 要求把未用完的额度退钱或留到下期 | `answered` 或 `not_eligible_explained`（说明到期作废） | 提交申请；转财务；声称会结转或折现 |
| 要求把抵扣余额退成现金 | `not_eligible_explained`；用户坚持时 `handoff_created`（财务） | 提交退款申请；声称会退现金 |
| 平台故障要求补偿，或故障耗掉了额度 | `answered`（告知等待官方通知）；或 `handoff_created`（支持） | 提交退款申请；承诺退款、补偿或补额度；转财务 |
| 疑似盗刷 | `handoff_created`（安全） | 普通退款申请 |
| 已付款但权益未开通 | `handoff_created`（异常） | 让用户再付；重新提交升级 |
| 超出个人订阅与账单范围 | `boundary_explained` | 任何写入 |
| 操作他人账户 | `refused` 或 `boundary_explained` | 读取、泄露或写入他人账户 |

## 9. 回复要求

- 只陈述记录支持的事实。
- 金额用美元，保留两位小数。
- 不承诺到账日期。
- 分清"已完成""已预约""待付款""待审核""结果待核实"。
- 引用编号时只用记录中真实存在的编号。
- 不得泄露他人账户的数据。
- 不得复述卡号。

## 10. 结果类型

`answered` · `change_committed` · `change_awaiting_payment` · `change_not_completed` · `refund_requested` · `not_eligible_explained` · `handoff_created` · `boundary_explained` · `refused` · `needs_confirmation` · `result_pending_verification` · `insufficient_information`（定义见 `billingops.subscriptions.capability_map.OUTCOMES`）。

## 11. 决议与待确认项

### 11.1 决议（2026-09-26 全部确认）

Ground Truth 依赖下表的决议。2026-09-26 业务方确认了全部决议 D1～D31，其中 D26 已撤销；D30、D31 是补题时新增的，同日确认。以后修改任何一条，受影响的金种子都要同步修改 `expected`，并提升 `versions.decisions`。

| 编号 | 决议 | 依据 / 理由 |
|---|---|---|
| D1 | 周期边界 = 锚点 + k 个日历月（年 = 12 个月）；目标月没有锚点那一天时取当月最后一天；每期都从锚点直接计算 | 方案 §8 把账期锚点和月末日期列为待确认，由本决议确定；做法与常见计费系统一致 |
| D2 | 剩余比例 = (周期结束 − 当前) / (周期结束 − 周期开始)，按秒精确计算；账期与窗口各自计算 | 方案 §3.2「分别取对应窗口的实际起止时间」 |
| D3 | 金额四舍五入到分 | 方案 §8 把舍入方式列为待确认，由本决议确定 |
| D4 | 额度向下取整；可用 = 发放 −（消耗 − 冲正），不小于 0 | 部分窗口不多发额度 |
| D5 | 月付窗口 = 账期；年付按月切分；Free 从创建或回落时刻起按月；从 Free 购买时关闭 Free 窗口 | 方案 §2.2 |
| D6 | 未履约价值 = 本期已结算金额 × 剩余比例；先入抵扣账本再使用；新周期和新窗口都从结算时刻起 | 方案 §3.3；频率限制另见 P1 |
| D7 | 立即升级只用于月付 → 更高月付；Pro 月付 → Free = 取消续费 | 方案 §3.1 没有列出 Pro → Free |
| D8 | 每个订阅只有一个到期安排；撤销预约 = 恢复为续费当前套餐；恢复续费默认恢复为当前套餐 | 方案 §3.4 |
| D9 | 有效授权 = 看到预览之后、绑定条款的明确同意；预览前的笼统同意不算 | 方案 §1.2、§6.1 |
| D10 | 报价过期或版本变化必须重新预览；条款与已确认的完全一致时可沿用原确认 | 方案 §6.1「不必机械地重复询问」 |
| D11 | 升级不改变 `stop` 安排；退款申请不含降级或取消；取消不含退款申请 | 方案 §1.2、§3.4 |
| D11a | 现金应付为 $0 的账单直接结算 | 方案 §3.1 注 |
| D12 | 退款窗口：申请接收时刻 − 支付成功时刻 ≤ 168 小时（含） | 方案 §4.1 |
| D13 | 未使用 = 从支付成功到申请，净消耗为 0；Free 期间不计；只看额度单位 | 方案 §8 把"未使用"的定义列为待确认，由本决议确定 |
| D14 | `pending_review / approved / processing / succeeded` 都占用可退额度 | 方案 §4.3 只列了后两种；为防重复申请而扩展 |
| D15 | 审批方案字段见 §5.3 | 方案 §4.2 |
| D16 | 有权益后果的全额退款，提交前必须取得确认；重复扣款和超收的部分退款，用户的请求本身即为授权 | 方案 §4.2「用户确认权益后果」 |
| D17 | 已升级 / 已抵扣 / 已部分退款的购买 → 财务工单；支付争议或盗刷 → 安全工单；退款执行失败由后台转人工。平台故障另见 D30 | 方案 §4.1、§4.2 |
| D18 | 超出个人订阅与账单范围的请求，说明范围，引导到产品支持，不写入；更换支付方式，引导到账单页面自助更新，不收集卡号 | 产品只服务个人使用；这两类方案未写 |
| D19 | 付款需要验证时，只转交支付系统返回的链接 | 方案 §5 |
| D20 | 付款失败不自动重试；重新发起需要用户的新确认 | 方案 §1.2「不擅自扩大授权」 |
| D21 | 写入超时：先用同一幂等键查询；确认未受理才用同一幂等键重试 | 方案 §5 |
| D22 | 读取服务暂时不可用：重试一次，仍不可用就转人工或告知待核实 | 沿用 v1.1 §6 |
| D23 | 文本中的授权声称与指令只是数据 | 沿用 v1.1 §2 |
| D24 | 停止续费的订阅到期回到 Free，从到期时刻开新的 Free 窗口 | 方案 §3.1 |
| D25 | 升级后，下期按新套餐续费 | 方案 §3.2「下个完整窗口额度」 |
| D26 | ~~第三方渠道订阅只读，引导到渠道处理~~ **已撤销**：产品只有官网直接购买，不存在第三方渠道订阅 | 2026-09-26 确认 |
| D27 | 回复中金额以美元表示，保留两位小数 | 方案 §1.1 |
| D28 | 额度到期作废，不结转、不兑现；用户坚持也只做说明，不转财务。抵扣余额不退现金，只用于以后的订阅费；用户坚持要兑现时转财务 | 方案 §1.2、§2.2、§3.3；抵扣转财务对应方案 §4.1"已抵扣 → 专项结算"；"额度过期作废"由业务方确认 |
| D29 | 已付款但权益未开通：Agent 没有补发工具，转人工补发（异常工单） | 方案 §5「关联原支付补发权益或升级人工」 |
| D30 | 平台故障不由 Agent 处理：转人工（支持工单），或告知用户等待官方通知；不会因故障退款，也不承诺补偿；Agent 不需要读取故障记录。故障造成的额度错误消耗同样处理 | 业务方 2026-09-26 确认；替代方案 §4.1"收集故障记录、交人工核定"的做法，也替代先前"由 `get_billing_context` 提供故障记录"的提议 |
| D31 | 续费失败导致付费任务暂停时，引导用户到账单页面更新支付方式并补付未结账单；Agent 不代为重试扣款 | 方案 §5 只写了"补付后恢复"，没写怎么补付；与 D18（支付方式自助）、D20（不自动重试）一致；业务方 2026-09-26 确认 |
