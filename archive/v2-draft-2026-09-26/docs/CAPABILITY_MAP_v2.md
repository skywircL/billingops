# 能力地图 v2（DevAgent 订阅与账单 Agent）

> 对应 [业务规范 v2（草案）](BUSINESS_SPEC_v2.md) 与 [Ground Truth v2](GROUND_TRUTH_v2.md)。机器可读版本在 `src/billingops/subscriptions/capability_map.py`，测试保证两者列出的叶子完全一致。v1（重复扣费台）的能力矩阵保留在 [CAPABILITY_MATRIX.md](CAPABILITY_MATRIX.md)，它仍是当前实现与 v4 评测的依据。

## 1. 怎么读这张图

- **能力地图不是功能列表。** 每片**叶子**是业务规范中一组走到同一个**可观察结果**的条件，结果包括：订阅、窗口和资金记录的变化，新建的申请或工单，明确的拒绝，或者什么都不变。叶子的 GT 列写的就是这个结果。
- **六个分支**，与方案 §7.1 一致：查询、订阅变更、续费管理、退款、异常恢复、权限与风险控制。
- **产品范围（2026-09-26 确认）**：只服务个人使用，即个人账户、官网直接购买、美元结算。方案 §1.1 的团队席位、企业合同、加量包、自动充值、超额自动扣款、第三方渠道订阅都不在产品中，这张图里没有它们的叶子。"明确不做什么"由三类叶子体现，每片都有明确的拒绝或引导结果：
  - Q-08：超出个人订阅与账单范围的请求；
  - F-15、F-16、F-17、S-08：不改退款目的地、额度到期作废、抵扣不退现金、不经手支付方式；
  - F-08、E-13：平台故障不由 Agent 处理，转人工或等官方通知，不会因此退款；
  - S 分支里所有"不应做"的叶子。

  2026-09-26 业务方确认了全部决议 D1～D31（D26 已撤销），包括这几片叶子的做法。
- **"修改"在哪里。** 按"根据用户要求、通过工具更新已有业务数据"来理解，"修改"对应 C（订阅变更）和 R（续费管理）两个分支。它们都只能通过合法业务操作留下新记录，不得改写历史账单金额，也不得删除支付记录（S-07）。退款单独成支，因为它动的是钱，而且出款不由 Agent 执行。
- **方向**：
  - "应做"：检验会不会做；
  - "不应做"：检验会不会克制；
  - "两者"：同一题里既要做对一件事，又不能多做另一件事，例如只报价不提交、提交退款但不降级。
- **风险**：
  - 只读；
  - 可恢复写入：到期安排变化，本期不动钱；
  - 扣款写入：购买、升级、跨周期；
  - 资金申请：退款申请，出款由后台完成；
  - 权限：越权、注入、支付凭证。

## 2. 标注维度（每道题都要标注）

| 维度 | 取值 | 说明 |
|---|---|---|
| 用户目标 `user_goal` | query / quote / purchase / upgrade / downgrade / cycle_switch / cancel / resume / revoke / refund / refund_status / report_problem / out_of_scope / other_account | 用户到底想完成什么 |
| 任务复杂度 `complexity` | single_read / multi_read / preview_only / preview_confirm_write / multi_turn_change / cross_object | 单次读取、多次读取、只报价、报价-确认-写入、中途改口、跨对象组合 |
| 输入质量 `input_quality` | full / partial / ambiguous / contradictory / conditional / adversarial | 信息完整、缺失、含糊、矛盾、有条件、对抗 |
| 系统状态 `system_state` | normal / payment_failed / requires_action / timeout_after_write / concurrent_change / entitlement_missing / refund_failed / duplicate_payment / authorization_hold / overcharge / quota_exhausted / suspected_fraud / scheduled_change / renewal_stopped / platform_outage / special_settlement / renewal_failed / quote_expired | 故障与业务状态分开写；"成功但响应超时"单列，不和"超时未执行"混用 |
| 风险 `risk` | read_only / reversible_write / money_write / money_request / permission | 见 §1 |
| 语言 `language` | zh / en / mixed | 美元结算，面向中英文用户 |
| 轮次 `turns` | 用户发言次数 | 由参考路径自动计算 |

不做笛卡尔积。先覆盖高频路径（查询、升级、取消、未使用退款），再补低频高后果的路径（超时、并发、盗刷、权益未开通），最后挑模型容易误判的交叉点（已取消时升级、取消覆盖预约、有条件退款、预授权）。

## 3. 规则树

```text
订阅与账单 Agent（个人账户 · 官网购买 · 美元）
├── Q 查询：套餐、额度、账单、订阅状态、变更报价、退款进度、抵扣余额、范围外请求
├── C 订阅变更：购买、立即升级、预约降级、周期切换、改口、未确认不得执行
├── R 续费管理：取消、恢复、撤销预约、新安排覆盖旧安排、已取消时升级
├── F 退款：7 天未使用、续费后未使用、已使用、超期、重复扣款、预授权、超收、
│          故障、专项结算、盗刷、有条件组合、未结申请、申请后使用、改退款目的地、兑现额度或抵扣
├── E 异常恢复：付款失败、需验证、续费失败、权益未开通、写入超时、重复通知、
│          并发修改、退款超时、退款执行失败、读取不可用、报价过期、错误消耗
└── S 权限与风险控制：他人账户、注入、审批隔离、不扩大授权、支付凭证、单次效果、不改写历史、更换支付方式
```

## 6. v1 机制到 v2 的对应

v1 的机制编号带前缀 "v1"，以免和 v2 叶子混淆。

| v1 机制 | v2 叶子 | 变化 |
|---|---|---|
| v1 D-01～D-28（重复扣费的目标识别与金额） | F-05、F-06 | 规则仍适用：第一笔为正常付款，其后为重复；按事实查全候选；编号冲突不替客户改退另一笔。v2 的处置从"提案 + 审批"改为"提交待审核申请"，并补充了"预授权不是重复扣款"（F-06） |
| v1 S-01～S-12（退款状态） | Q-06、E-10 | 状态从 pending / completed / failed 扩展为六个状态；failed 必须说明"未完成、由人工处理" |
| v1 P-01～P-05（价格解释） | Q-01、Q-03、Q-04 | 价格版本取代 v1 的 `price_change` 事件 |
| v1 P-06、P-07、P-09（订阅退钱一律升级） | F-01、F-02、F-03、F-04、F-07、R-01 | **规则变了**：7 天内未使用可以提交申请；已使用不退，但可以取消续费；超收可以部分退款。v1.1 的"一律升级"不再适用 |
| v1 X-01～X-04（越权与注入） | S-01、S-02 | 不变 |
| v1 E-01～E-06（审批、执行、核验） | F 分支 + E-06、E-09、E-10 | 出款从"代码执行、Agent 核验"变成"后台执行"；Agent 只负责申请、查询和如实说明 |
| v1 E-09、E-10（读取故障） | E-11 | 沿用 v1.1 的"重试一次，仍不可用就转人工" |

## 7. 缺口与下一步

1. **有叶子、没金种子（13 片）**：
   - Q-01、Q-03、Q-04；
   - C-03、C-06、C-08、C-09；
   - F-02、F-14；
   - E-07、E-11、E-13；
   - S-07。

   这些叶子的规则都已确定，可以随时补题。其中 C-03 与 C-02 的规则相同；E-07 主要靠后端保证。
2. **多轮**：改口、答非所问、中途切换任务，这几类只有一道题。按文章的做法，应该用受控变异从现有金种子扩出来，而不是新写孤立的题。
3. **v2 环境**：v2 的计费环境、工具实现和评分器都还没有，现在的金种子只能做静态校验（见 [Ground Truth v2 §5](GROUND_TRUTH_v2.md#5-验收与现状)）。
