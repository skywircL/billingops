# v2 环境设计（待评审）

> 目标：让 [Ground Truth v2](GROUND_TRUTH_v2.md) 的 39 道金种子能在真实环境里跑通，并为下一步的 v2 Agent 提供同一套工具和服务。
> 依据：[业务规范 v2](BUSINESS_SPEC_v2.md)（决议 D1～D31 已确认）。
> 状态：**设计稿，等业务方评审后再写代码**。本轮不改 v1 的任何代码，也不调用模型（花费 $0）。

## 1. 这一轮要交付什么

1. **一个独立的模拟订阅服务** `subscription_service`：独立进程、独立 SQLite。v1 的 `billing_service` 保持不变，v1 的评测照常能跑。
2. **Agent 工具层**：8 个业务工具的 HTTP 客户端和工具定义，按身份限定只能访问本人账户。
3. **参考执行**：对每道金种子，加载初始世界，按参考路径真实调用服务，模拟用户回答、时钟推进和中途事件，最后把服务里的实际状态和 `expected` 比对。**验收标准：39/39 通过。**
4. **评分器 v2 的前两层**：结果层（状态比对）和行为层（不变量、禁止动作）。表达层沿用现有的 j4 裁判。

**不在本轮**：v2 Agent 本身（A 固定流程 / B 动态调查怎么做，下一轮再定），以及真实模型的评测运行。

## 2. 总体结构

```text
参考执行 / 以后的 v2 Agent
   │  工具调用（带身份）
   ▼
ToolRunnerV2 ── SubscriptionClient（HTTP）
                      │
                      ▼
            subscription_service（FastAPI + SQLite，独立进程）
              ├─ 业务操作：报价、提交、续费任务、退款预审与申请、工单
              ├─ 金额与额度：全部调用 billingops.subscriptions.policy（与出题复算用的是同一份代码）
              ├─ 模拟时钟、行为注入、中途事件（只有 /_admin 可以改）
              └─ 世界的加载与导出（供评测比对）
```

后端自己负责守住各项约束（方案 §1.2"约束由后端实施"）：
- 身份范围；
- 报价是否过期、版本是否变化；
- 确认是否绑定了条款（见 §5）；
- 退款金额只能是预审结果；
- 幂等；
- 工单里不能出现卡号。

评测时，这些约束靠两条互相独立的线来检查：一是后端会拒绝违规请求，二是评分器会检查调用轨迹。

## 3. 数据模型

| 表 | 关键字段 | 说明 |
|---|---|---|
| `accounts` | `owner_user_id`、`type` | 只有个人账户 |
| `subscriptions` | `plan`、`cycle`、`status`（`active / past_due / ended`）、`current_period_*`、`renewal`、`version` | Free 也用一条记录表示（`plan = free`）；每次变更 `version + 1` |
| `usage_windows` | `start`、`end`、`granted / used / reversed`、`status` | 可用额度 = 发放 −（消耗 − 冲正） |
| `invoices` / `payments` | 见契约 §2.2 | 付款状态：`succeeded / failed / requires_action / authorized / voided` |
| `credit_ledger` | `grant / use` | 抵扣余额 = 所有 grant − 所有 use |
| `quotes` | 条款、条款摘要、订阅 / 价格 / 政策版本、`expires_at`、`status` | 10 分钟有效；只用于报价，不改业务状态 |
| `confirmations` | `quote_id` 或 `eligibility_id`、条款摘要、`decision`、时间 | 见 §5 |
| `operations` | `idempotency_key`（唯一）、请求摘要、结果 | 同键同请求返回原结果；同键不同请求返回 409 |
| `refund_requests` / `handoffs` | 见契约 §2.2 | 工单的关联记录必须属于本人账户 |
| `clock` / `behaviour` / `events` | 当前时刻；付款和超时行为；中途事件 | 只能通过 `/_admin` 修改 |

## 4. 工具与后端规则

| 工具 | 后端做什么 | 后端拒绝什么 |
|---|---|---|
| `get_billing_context` | 返回本人账户的订阅、到期安排、当前窗口、近期账单与支付、抵扣余额、退款申请、工单 | 读取他人账户（统一返回 not found，不确认对方是否存在） |
| `list_plans` | 套餐目录和价格版本 | — |
| `preview_subscription_change` | 按规范 §4 计算条款：现金应付、使用的抵扣、额度变化、生效时间、到期安排，以及会被替换的旧安排（R-04）；生成报价 | 不合法的变更，例如同一周期内立即降级、年付立即升到年付 |
| `commit_subscription_change` | 按行为设置扣款，成功后才改订阅、窗口和抵扣；写入操作记录 | 报价过期（`quote_expired`）；订阅版本已变（`quote_stale`）；缺少绑定条款的确认；幂等键冲突 |
| `evaluate_refund_eligibility` | 按规范 §5.1 判定：未使用、重复扣款、超收、需专项结算；返回金额和方案 | — |
| `create_refund_request` | 重新预审一遍，只接受预审得出的金额和方案；状态为 `pending_review` | 金额与预审不一致；不符合资格；有权益后果的申请缺少确认；幂等键冲突 |
| `get_operation_status` | 按幂等键、操作编号、申请编号或工单编号查询结果 | 查询本身不产生任何写入 |
| `create_handoff` | 创建财务、安全、异常或支持工单 | 关联记录不属于本人账户；摘要里有卡号一类的数字 |

`ask_customer` 和 `finish` 属于对话层，不经过服务。

**续费任务**：只能通过 `/_admin/run_renewals` 触发，时钟推进到周期结束时执行。按到期安排分三种情况：
- 续费：按 `policy.renewal` 计费，先用抵扣再扣现金；
- 切换：换成新套餐或新周期，再按新价格续费；
- 停止：回到 Free。

扣款失败时，订阅状态改为 `past_due`，续费账单保持 open，不发放新窗口（ERR-04）。金种子的 `after_clock` 就是靠这个任务来验证。

**行为注入**：
- 付款：成功、失败或需要验证；
- 写入后超时：提交变更已生效但响应超时（ERR-01），退款申请已创建但响应超时（ERR-03）；
- 中途事件：第 n 次调用某个工具之后，改动世界（SUB-12 的控制台升级）；
- 用户延迟回答：模拟用户的 `delay_seconds` 会让时钟往前走（SUB-18 的报价过期）。

## 5. 需要你拍板的一件事：确认怎么绑定到条款

决议 D9 和 D16 要求用户的确认必须**绑定具体条款**，比如"$40.00、Max 5x、立即生效"。问题在于由谁来保证这一点。

| | A. 结构化确认（建议） | B. 自由文本确认 |
|---|---|---|
| 怎么做 | `ask_customer` 可以带上 `quote_id`（或退款预审编号）。用户看到的条款由**系统根据报价生成**，不是模型转述的；用户的"是 / 否"作为一条确认记录写进服务。`commit` 必须带这条确认的编号，后端核对确认的条款和报价的条款一致 | 模型自己写问题，用户用文字回答。后端不知道用户确认的是什么，只能事后由评分器检查轨迹 |
| 能防住什么 | 模型报错价格、漏说"会替换已有预约"、拿过期报价的确认去提交新报价——这三种情况后端都会直接拒绝 | 都只能靠评分器事后发现，线上无法拦截 |
| 代价 | 契约增加两个字段：确认步骤带上 `quote_id`，提交步骤带上 `confirmation_id`。金种子的参考路径需要机械地改一遍，题意不变 | 不用改 |

我建议选 A：它把"确认绑定条款"从提示词层面挪到了后端，正是方案 §1.2 说的"约束由后端实施"，也和 v1 里"审批绑定提案指纹"的做法一脉相承。报价过期时，只有新报价的条款摘要和已确认的完全一致，才可以沿用原来的确认，这就是 D10 的后端实现。

## 6. 参考执行与评分

**参考执行**（`evaluation/reference_v2.py`）：
1. 为每道题新建一个服务实例和临时数据库，加载初始世界，设好时钟和行为；
2. 按参考路径逐步调用工具。遇到 `ask_customer` 时，由模拟用户按脚本回答：结构化确认记为"是"或"否"，有延迟就先推进时钟。按调用次数触发中途事件；
3. 导出服务状态，和 `expected.state` 比对；有 `after_clock` 的题，推进时钟、运行续费任务后再比对一次；
4. 输出每道题的结果和差异。验收标准：**39/39 通过**。

**状态比对**（`evaluation/projection_v2.py`）：
- 订阅和窗口：只比对 `expected` 里写到的字段，其余字段必须保持初值；
- `new_*` 列表：必须完整对上，一条不多一条不少；
- 工单的 `links`：按"至少包含这些记录"比对；
- 另外支持 `status_any` 和 `any_of` 两种写法。

参考执行和以后的评分器用同一份比对代码。

**评分器 v2**：
- **结果层**：状态比对（用上面同一份代码）；
- **行为层**：不变量（按调用轨迹，并结合服务的操作记录）、禁止动作、是否提问；
- **安全**：没有写入他人账户、没有重复的业务效果、任何记录里都没有卡号；
- **表达层**：沿用 j4 裁判和各题的断言。

另外会把 `tests/test_gt_v2.py` 里的错误改法（跳过确认、换幂等键等）对应到"坏轨迹"上，确认评分器会判它们失败。
