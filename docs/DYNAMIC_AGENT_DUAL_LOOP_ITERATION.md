# 动态 Agent：双 Loop 归因与 B2 迭代

本轮按[美团《Agent 评测白皮书》§1.2](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html)区分两条迭代链：Agent 本身没有完成业务，修改 Agent；标准判错、覆盖遗漏或模拟环境不符合契约，修改评测。一个 case 可以拆成多个问题，分别进入两条链。本文项目证据是模拟业务和实际模型运行轨迹，不是线上人工工单，也未经外部业务专家背书。

## 归因入口与结果保护

入口固定为 B1 最新合并结果：735 条原记录 + 9 条用户授权重试，128 题/744 个逻辑试验，592 pass、123 fail、29 unknown。原始报告、运行记录、裁判输出和 80.21% case 等权任务成功率全部保留。

[逐试验归因库](../analysis/dynamic-eval-v1/B2-dual-loop-case-registry.json)覆盖 123 fail + 29 unknown，保存原标签、证据路径与哈希、问题来源、Loop、证据强度和人工审核状态。路由包括候选归因，不等于人工确认的根因计数。没有充分证据的条目保持 unresolved，不能把 unknown 自动归为 Agent 错误。

## 独立版本与预算

- Agent：`Settings(agent_revision="B2", mode="dynamic")`；B0/B1 保留原行为入口。B2 输出和 schema 变动独立登记。
- 确定性评分：`business-v2-trace-1.2`。
- 回复评分：`business-v2-response-1.3`，新增逐消息金额校验与严格时间边界；仍是待人工校准的语义裁判。
- 模拟客户：`v2-controls-1.6`；Runner：`v2-runner-1.6`。
- 题库：原 128 题及受控变异契约不变；新公共回复检查在评分时叠加，不反写冻结题目或答案。
- 普通 Agent 调用输出上限 4096；协议恢复上限 `min(2×base,8192)`；抽取最多一次额外调用，调查仍限 14 次调用/8 次读取/2 次询问/2 次修复。恢复预算改变要报告成本与时延，不能称为相同 token 预算下的纯提示词收益。
- DeepSeek 默认 thinking 下不支持 `tool_choice=required`。通过显式 provider capability 选择实际 `auto`，提供工具 schema 并在本地校验单工具调用；不关闭 thinking、不吞 HTTP400，不宣称 API 已强制工具输出。[官方 API 说明](https://api-docs.deepseek.com/api/create-chat-completion/)

## 两种验证不能混算

**评测 Loop：固定轨迹，比较量具。** 已对原 B0/B1 各 744 个逻辑试验进行不调用模型的旁路复核，分别有 28/63 条确定性断言变化。B1 的 63 条中，28 条是拒绝审批判定，35 条满足只读终态映射。新增公开金额规则和历史消息时间评分尚待语义重评，不能拿这批部分新标签计算“修正后任务成功率”。见[旁路报告](../analysis/dynamic-eval-v1/measurement-v1.2-offline-review-v2/report.md)。此报告绑定当时 response 1.2 源码；后续 1.3 时间边界修复另有版本记录。

**Agent Loop：固定新版量具，比较 B1/B2。** 使用 `scripts/run_dual_loop_pilot.py` 在运行前固定 30 题，两版本各一次，共 60 次。覆盖已见缺陷，也包含正常退款、真实调价、仅解释、权限拒绝、撤回、目标更正和写后丢回执对照。两组使用同一题库、DeepSeek 配置、评分器、模拟客户及运行预算；B2 的恢复预算是显式 Agent 改动。单次诊断用于发现退化，不替代每题 3/7 次的完整评测，不作为新的简历成功率。

首轮 `runs/dynamic-dual-loop-B1-B2-pilot-1` 暴露了请求兼容性与公开回复缺少时间边界的问题。发现问题时两组已先后启动，60 条尝试均保留；产生 HTTP400 的请求在 B1/B2 分别涉及 5/16 条试验。停止正式比较，源码漂移防护未生成成对总成绩；保留独立 `iteration-stop.json` 解释原因。后续修复使用新的完整登记，不只重跑失败题。首轮费用也计入实际消耗。

## 验证与尚未完成的工作

- 修复第一批边界问题后完整兼容与回归 **816 passed**，记录 `analysis/dynamic-eval-v1/B2-compatibility-v1.txt`。
- provider 兼容和公开消息时间采集修复后完整回归 **830 passed**，记录 `analysis/dynamic-eval-v1/B2-compatibility-v2.txt`。
- 第二轮 `runs/dynamic-dual-loop-B1-B2-pilot-2` 在 B1 的末尾遇到 **11 次裁判 HTTP402**，涉及 G02/G14/G17/G29。收集完已提交的 30 条后停止；B2 未启动，未生成正式 summary 或成对成绩。不能把 API 中断算成业务修复失败，也不能报 B2 新成功率。
- 第二轮 239 次 Agent 调用、6 次模拟客户调用均使用实际 `auto`，没有 HTTP400。G06/G07/G12/G13/G14 共 6 次真实客户交互均有合法条件匹配及相应业务状态证据；这支持模拟客户局部修复有效，不代表 B2 已被真实模型验证。
- 两轮共实际执行 **90 次试验**，估算总模型费用 **$1.4205**，包含无效首轮及中断末轮消耗；估价来自冻结 token 价格，不替代服务商账单。源码冻结副本与注册哈希一致。详见[本轮验证记录](../analysis/dynamic-eval-v1/B2-iteration-validation.json)。
- G25 中文/英文“联系产品支持”出现裁判相反标签，已进入[裁判校准队列](../analysis/dynamic-eval-v1/B2-judge-calibration-queue.json)。这是复合 rubric 的边界歧义候选；原标签保留，不借其中一次 pass 宣称问题已解决。B2 产品回复已去除无依据渠道，裁判一致性仍需单独校准。
- Gold 用户逐题审核、语义裁判独立人工校准及 Hidden 集仍未完成。无真实历史工单，不能把模拟结果说成线上收益。
- 每个改动同时保留 badcase 和正常/反向对照：无授权不能退款、真实调价不能被重复付款替代、无法确认的客户不能替其选择、合法拒绝不能被当漏处理、正确进度回复不能被未来状态否定。
- 后续完整比较必须让 B1/B2 使用同一最终评测版本并重新登记。仅修评分或模拟环境带来的变化属于评测 Loop；只有同一量具下的实际 Agent 改动收益才能进入 Agent 修复结果。
