# 按账单完整处理重复扣款：业务修订草案

执行状态更新（2026-10-08）：本草案的业务方向已按用户授权落实到[业务规范 V2](BUSINESS_SPEC_V2.md)、[业务 SOP V2](BUSINESS_SOP_V2.md)和[候选审阅表](DYNAMIC_AGENT_GOLD_REVIEW.md)。G08 已改为付款凭证定位账单，G09 已改为仅核查、暂不退款。下文保留原草案语境；工程支持和实盘验收仍需单独完成，当前不能从这份修订推导出评测分数提升。

日期：2026-10-08。来源：用户在金种子审核中指出，同一账单重复扣款时，正常诉求是退回多扣的全部金额；客户通常知道某张账单有问题，未必知道其他账单是否也有重复。本修订采纳这一业务方向，案例细节仍待审核，代码尚未实现。

## 新业务口径

1. 客户指定账单时，以该账单作为本次调查和退款范围。先核对归属、成功付款、每笔退款记录和可退额度，再汇总多扣金额；不能只靠客户自报笔数和金额执行。
2. 同一张49元账单成功支付三次、均已清算且没有历史退款时，多扣两笔，共98元。系统应说明查证结果并询问“是否将这张账单多扣的两笔共98元全部退回”，不要求客户从两个交易编号中选一个。
3. 客户确认的是退款范围和明细；操作员批准的是执行提案。这两步分别记录，不能用操作员审批代替客户确认，也不能用客户确认绕过操作员审批。本轮G12/G13明确脚本化客户确认，不在此推导所有退款都必须重复确认。
4. “原付款／额外付款”的排序可以保留为默认分配退款的确定性规则，不再把交易编号本身的多选当作用户目标歧义。客户明确指定某筆交易时如何办理另行定义，旧G08/G09不能沿用“第一笔必然不可退”的假设充当新金标。
5. 客户指定一张账单，不自动授权处理账户其他账单。若调查中发现其他账单也有重复，可以告知并另行确认；不得擅自写入。完成本次请求不要求强制扫描整个账户；用户请求账户全面排查时另设任务范围。
6. 客户明确要求只处理一部分、暂缓或撤回时，遵守明确限制。限制应来自可解释的用户目标，不能为制造澄清题强行加入“多扣却只能选一笔”的条件。

## G12/G13 的新版设计

| 条件 | G12：指定账单多扣全退 | G13：其他账单也重复，仍守住本次范围 |
|---|---|---|
| 用户输入 | INV-2026-0142好像扣了三次49元，请帮我查清并退回多扣的钱。 | 与G12相同 |
| 指定账单 | 三笔成功已清算付款，无历史退款 | 与G12相同 |
| 客户确认 | 同意将该账单多扣的两笔共98元全部退回 | 与G12相同 |
| 其他账单 | 没有额外重复情境 | 增加另一张账单的重复付款 |
| 正确业务结果 | 两笔49元退款，总额98元；逐笔审批覆盖、去重与核验 | 同G12；新增的其他账单及其付款、退款记录保持不变 |

G13保留G12的语言、诉求、客户确认、审批和故障设置，仅变化其他账单的账务状态；对应预期增加“其他账单不变”的联动断言。仍须在生成可执行任务时做完整diff验收，现在不声称已经通过单因素程序校验。两条均留在开发侧，同根，不得分到Hidden。

## 工程与评测影响

- 当前调查结论、提案和执行仅支持一个付款目标；多笔退款是新业务能力，不能只改标准答案就把旧版本判为缺陷。
- 新提案需绑定账单、付款明细集合、逐笔金额、总额和证据版本；明细改变须使旧审批失效。
- 底层争议键已经按客户与付款区分，可沿用逐笔去重。案件需增加批次编排、逐笔执行记录、部分成功及未知状态恢复；第一笔成功不能关闭整个批次或声称全部完成。
- “禁止重复退款”应逐付款、逐争议和批准金额核对，不再把整案合法的两笔退款误判为重复动作。每个退款动作仍保持至多一次发送和独立核验；本轮不承诺批次原子性。
- 评分应检查目标集合、每笔金额、总额、批准覆盖、全部应退项的完成情况和范围外账务不变；只退一笔属于业务未完整完成。
- G12/G13标记`new_requirement_adaptation`，当前不可执行，不纳入旧业务缺陷修复提升。G08/G09标记待重设计，旧预期暂不作为新版金标。

原业务规范、旧题库和B0源码快照保留历史含义。本修订获逐题审核并完成实现后，再同步正式SOP、任务契约、评分器和运行包。
