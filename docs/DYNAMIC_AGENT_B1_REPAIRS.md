## 变更范围

| 已观察到的问题 | B1 实现 | 验证重点 |
|---|---|---|
| G01：只读额外付款退款，漏掉原付款余额 | 完整账单净额与所有成功付款退款共同校验；账户完整退款查询可提供等价证据 | 未读不能当零退款；历史退款不能换付款编号绕过 |
| G08：付款凭证误当唯一退款目标 | 独立记录退款/仅核查诉求，区分账单定位凭证与明确交易限制 | 定位凭证可定位账单；明确限制不得扩大 |
| G06/G07/G14：最终回复请确认，实际上已结束案件 | 可纠正的编号缺失或冲突进入真实客户等待，保存命令和回答 | 状态为 awaiting_user；更正后才重算目标 |
| G09：仅核查错误归入退款或信息不足 | inquiry_completed 只读终态与退款授权独立 | 没有提案、审批和退款写入 |
| G14：调查读到付款，但回复说未查到 | 完整记录索引、请求范围、空结果及失败证据传入回复 | 未读/读失败/读到空/独立读到另一账单不可混淆 |
| G12/G13：三次扣款仍只能退单笔 | 整账单分配、完整范围客户确认、绑定全部明细与总额的审批、逐笔幂等执行与核实 | 属于新增业务能力；不得只靠 prompt 声称修好 |
| G31/P1：他人账户请求无依据转人工 | permission_refused 并解释权限范围 | 不替客户换绑定，不访问或披露他人记录 |

批量执行需要额外的工程保护：Billing 事务内同时检查单笔余额与整张账单超收上限；根账本记录整批，子账本记录各次动作，回执丢失时先核实而不重发。执行中撤回和目标变化应停止尚未发送的动作；已发送的动作继续核实，不能声称撤回了已完成的退款。

## 版本与比较口径

- 新实现由 `Settings(agent_revision="B1", mode="dynamic")` 显式选择；历史 B0 / 固定流程保留兼容入口。服务事务内的账单总额保护是共同执行安全增强，不是模型算法提升。
- 运行入口：`python -m billingops.evaluation.v2_runner data/tasks/dynamic-v2/controlled-coverage-v1.json --mode unified --agent-revision B1 --workers 16 --out runs/dynamic-v2-B1-unified-1`。
- 128 个 case、试验次数与排序随机种子、DeepSeek 型号及参数、公共业务上下文、任务和裁判时限、customer controls、response grader、trace scorer 均沿用完整 B0。
- Runner 1.4 只新增实现版本选择和登记，未改变评价逻辑；实际源文件差异必须在 B1 冻结时逐项记录 SHA 与原因。B1 包含工具/业务执行能力增加，因此对比是系统版本改进，不能写成纯 prompt 或模型能力提升。
- 比较分别报告 Outcome、Behavior、必要回复、Task Success、未知、成本/延迟、各类失败变化；资金、权限、重复写入及隐私单独列出，不能和成功率加权。
- 多笔退款能力单列；同一冻结开发集上修复后复测仍是探索性结果。无 Hidden，模拟 Gold 和裁判仍待独立人工审核，不能宣称生产安全或泛化结论。

应用演示可用新的数据库启动：`python -m billingops.api --mode dynamic --agent-revision B1 --model openai --db data/b1-app.sqlite3`。审批页面显示所有付款明细和总额，按钮绑定操作者实际看到的版本；执行回执按每笔展示。
