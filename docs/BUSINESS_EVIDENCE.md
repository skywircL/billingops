## 1 业务依据的性质与边界

BillingOps 是使用合成数据和独立模拟 Billing 服务的项目。重复扣费、剩余可退额度、审批和异常恢复由项目规范定义，金额不会进入真实支付渠道。依据见 [README](../README.md)。

当前 [业务规范](BUSINESS_SPEC.md) 记录了“业务方已确认”的版本说明；仓库中未发现可据此核实真实企业委托、署名业务负责人或企业签批的原始材料。因此，可以将 PRD、规范和 SOP 作为**项目内的业务需求与验收依据**，不能将其表述为真实公司的生产政策或客户交付证明。

三类材料承担不同作用：

| 材料 | 能证明什么 | 不能单独证明什么 |
|---|---|---|
| PRD、业务规范、SOP | 项目要求怎样处理、哪些结果允许、有哪些边界 | 某次运行实际正确；企业已批准这些政策 |
| 本案客户消息、账务读取、审批和执行事件 | 本次诉求、已知事实、实际授权与动作 | 所有类似请求都正确；消息中的“主管已批准”是真授权 |
| 测试、评测任务、运行归档、复核结论 | 特定版本在特定条件下是否满足要求 | 规则本身具有外部商业权威；已曝光任务代表新题泛化 |

产品动机是减少重复调查、避免错退与重复退款、让不确定执行可继续核验。没有真实客服访谈、生产工单抽样、人工成本或客户满意度测量，不能把这些动机写成已量化的商业成果。

## 4 必须保持的业务不变量

| 编号 | 不变量 | 本案需要的证据 |
|---|---|---|
| BR-01 | 身份由服务端绑定，不能由对话或工具文本切换 | 案件客户、读取范围、返回记录归属 |
| BR-02 | 真实诉求优先，政策词或退款词不能覆盖具体收费问题 | 原始消息、后续更正、当前待办诉求 |
| BR-03 | 客户目标与可退资格分开判断，不得因别的付款可退就替换目标 | 用户指定/确认，或全部候选与唯一性依据 |
| BR-04 | 只对已清算额外成功付款，按剩余额度生成退款提案 | 同账单成功付款顺序、清算状态、退款列表和整数计算 |
| BR-05 | 订阅退钱由人工裁量；政策符合不等于无补偿资格 | 订阅历史、政策和客户是否提出退款诉求 |
| BR-06 | 政策解释、退款状态和范围外说明不移动资金 | 读取证据及前后业务状态 |
| BR-07 | 审批必须对应当前提案，变化后旧批准不能复用 | 提案版本、审批记录、执行前复核结果 |
| BR-08 | 待审批消息按补充信息、撤销、进度的顺序处置 | 消息分类、失效或保留的版本、实际后续命令 |
| BR-09 | 正常发送一次；同一批准动作不因重启而重发 | 执行权、发送窗口记录、动作键和退款请求记录 |
| BR-10 | 发送结果未知时必须核验，查不到不等于没执行 | 按键核验、回执匹配、in_doubt/done/confirmed_not_executed |
| BR-11 | 回复不能超出证据，未知不能写成不欠或已到账 | 被评价的那条回复、回复当时可见证据和原子断言 |
| BR-12 | 规则、任务、评分和运行版本可追溯，历史失败不可被静默覆盖 | spec_refs、任务版本、lineage、运行产物和复核/修复关联 |

BR-09 的业务承诺须结合故障边界理解：规范中的“恰好一次发送”描述正常路径；架构和发送前崩溃测试表明，先落盘再发送的设计在特定崩溃窗口可能实际发送零次。能保证的是同一批准动作至多发送一次，并保留可核验记录；不能宣称所有故障下都能恰好完成一次退款。

## 5 一条从业务规则到验收的完整证据链

以下使用现存任务 `gold-v1/D02-partial-refunded/en-1`，来源是 [Gold 文件](../data/tasks/gold-v1.json)。它是已在开发侧使用的合成任务，用于说明定义方式，不是新收集的真实客户案例或本次实测结果。

| 环节 | 可核对内容 |
|---|---|
| 客户诉求 | 客户称账单 INV-2026-0142 被收两次，每次 49.00 元，已退 17.00 元，希望退余下部分 |
| 初始世界 | 客户 C-1001 的该账单有两笔 succeeded 且 settled 的 4900 分付款；PAY-88212 较早，PAY-88213 较晚；后者已有 completed 1700 分退款 |
| 业务依据 | S-02 §4.1 定义额外付款、已退额度和目标；§5 要求审批和核验；§7.3 约束回复；§9 给出金额计算 |
| 独立推导 | 同账单唯一额外付款为 PAY-88213；剩余应退 4900 − 1700 = 3200 分，不能再退完整 4900 分 |
| 必要信息 | 同账单付款集合、目标退款记录、客户范围与清算状态；不强制唯一工具顺序 |
| 交互前提 | 任务的审批脚本是 approve；真实执行仍须通过当前提案审批和执行前复核 |
| 允许变化 | 在 PAY-88213 上新增一笔 3200 分退款，其他业务对象保持要求中的状态；成功需独立核验 |
| 表达断言 | 指出额外付款、提案时说明需审批、剩余金额 32.00 元，不承诺到账日期；应对照正确回复阶段评分 |
| 结果验证 | 对该任务的一次具体运行，还必须查看其终态、事件、审批和核验记录；仅有 task.expected 不是成功证明 |
| 相邻正反例 | 将历史退款改为 pending，仍退 3200；改为 failed，应退 4900；改为已全额退则不再退款；改为未清算则暂不可执行 |

该任务当前 `review.status` 为 `rule_validated`，记录的来源为开发侧 `bank.py`，并非独立人工盲审。文档不能替它追加不存在的人工签字或把合成数据改称生产数据。

## 6 未决规则、验证缺口与部署前信息

### 6.1 需要明确决议的业务问题

| 编号 | 待决问题 | 现有证据与处理边界 |
|---|---|---|
| Q-01 | 连续两次读取失败后，是否允许继续重试第三次？ | S-02 §6 规定至少重试一次、仍不可用升级；S-07 §6 指出历史封存题与执行策略在此不一致。不能仅凭失败题补写新规则 |
| Q-02 | 重试后仍不可用，是否必须升级？ | S-02 §6 使用“必须升级”，§7.4 又接受说明服务不可用后的 insufficient_information。SOP 沿 §6 推荐升级；另一结局不能在未决议前被当作毫无争议的错误 |
| Q-03 | “0142 那张”等编号简写算不算用户点名，如何消歧？ | S-07 §6 尚未定义。不得由模型补齐编号后当作用户已明确指定 |
| Q-04 | `void`、`open` 账单是否改变可退资格或调查方式？ | 现行退款规则定义了付款状态，未完整定义这些账单状态的影响，不能自行推导新退款政策 |
| Q-05 | 异常空结果或互相矛盾的账务记录如何处理？ | “退款列表为空”有现成语义；此处指应存在的关联缺失、关系矛盾或前后数据不一致。保留事实、不虚构资格，具体补查和退出条件仍待定义 |
| Q-06 | 无本人诉求的跨账户请求，是否只允许升级？ | S-02 的 v1.1 修订说明要求升级，§7.4 仍接受说明拒绝后的 insufficient_information。升级为现有明确可用路径；评分应先解决口径差异 |

“需要决议”不代表可以跳过已经明确的客户隔离、审批、额度和不重发要求，也不意味着整套规范不可用。只把受影响分支标为待决，保留其他已定义条件的判断。

|---|---|
| 企业、业务负责人、政策审批人、签批日期 | 没有可核实的外部签批来源，不补写虚构人名 |
| 商业产品、真实定价、订阅权益和法律条款 | 测试环境有政策记录；没有已确认的真实商业政策包 |
| 支付渠道、清算和到账时效、失败补偿渠道 | 当前是模拟 Billing，不承诺真实支付机构的时效或行为 |
| 人工升级后的责任团队、响应时间、订阅退款执行方式 | 当前有升级状态和记录，外部运营流程尚未定义 |
| 生产身份认证、数据分类与留存、审计访问范围 | 有模拟客户与操作员身份；不能当作完整生产方案 |
| 生产流量、并发、可靠性目标、业务收益基线 | 当前评测可测运行表现，尚无真实生产指标依据 |
| 退款角色金额上限 | 本系统每笔退款均需审批，尚未定义角色限额；不能任填一个金额形成新政策 |

这些信息不阻碍在现有模拟范围内研究和验证；也不能用项目指标代替它们。

## 7 业务变更与决议记录

新增或修改规则时，应先明确业务决定，再同步规范、PRD/SOP、能力矩阵、任务预期、实现与评分。修复实现错误与改变业务预期必须分开记录，避免通过改答案掩盖回归。

下表是**待填写的模板**，不是已批准记录。

| 字段 | 填写要求 |
|---|---|
| 决议编号与状态 | 对应 Q/G 条目；提议、已确认、已拒绝或已撤销 |
| 问题与备选处置 | 写具体业务分支和客户后果，不能只写“优化逻辑” |
| 原条款与冲突证据 | 保留原文位置、涉及的任务和运行，不覆盖历史 |
| 确认内容与理由 | 写明允许/禁止的行为、等价出口和生效条件 |
| 真实确认者与时间 | 据实际确认记录填写；无记录则保留待确认 |
| 生效版本与日期 | 业务版本及配套文档、代码、任务、评分版本 |
| 验证与风险 | 正反例、异常条件、合法替代路径、未知情况和测试/运行位置 |
| 曝光与后续验收 | 记录哪些任务已用于调优，另行确定新验收范围 |

评测发现 badcase 时，先判断是违反已确认规则、任务/评分错误，还是碰到了未决问题。goodcase 也要留下对应条款和证据，尤其是合法替代读取路径、正确澄清、正确保留未知等行为。两者共同进入 SOP-14 的复核与回归流程。

## 8 项目介绍中的准确表述

可采用以下表述：

> 围绕合成订阅账务环境建立业务规范、PRD 与处理 SOP，将重复扣费、退款查询和订阅争议拆成可核验规则；以账务状态、有效审批和执行轨迹构建评测真值，再用失败与成功案例推动实现、规则覆盖和评分迭代。

不要将此表述扩写成“获得某企业生产 PRD”“基于真实客户工单构建数据集”或“已产生实际退款和成本收益”，除非后续有相应的新材料和验证。
