# BillingOps 项目面试口述长稿

面向字节跳动 Data AML 方舟平台 Agent 基础系统与评测基础设施实习岗位。

以下以当前工作区的 BillingOps 为简历项目，采用第一人称口述，按“项目总述—实现细节—评测与迭代—岗位迁移”展开。第一段用于开场，后面的内容用于顺着面试官的追问深入展开；整篇是完整练习素材，不需要在一次自我介绍里连续念完。项目能力与实验数字依据仓库已有代码和归档记录，最新覆盖评测记录截至 2026 年 9 月 27 日。

**一、先把项目的主线讲清楚。** 我介绍一下我的 BillingOps 项目。它是一个处理账单争议的 Agent，主要覆盖重复扣费调查、退款进度查询，以及订阅价格争议。用户可以直接用自然语言描述问题，系统查询账单、付款和退款记录，必要时向用户补充提问，再给出有证据的结论。如果确实涉及重复扣费退款，就生成提案，经过人工审批之后执行，并独立核验结果。

这个项目里，我主要围绕三个问题做工作。第一，模型面对不完整的信息，能不能把任务调查清楚。第二，涉及会改变外部状态的操作，系统怎样控制权限、审批、重复执行和异常恢复。第三，怎么建立一套可以反复运行的评测，让我知道改动到底解决了什么问题，有没有引入新的退步。

所以如果用一句话概括，我做的是一个有明确执行边界的业务 Agent，以及围绕它构建的评测和案例迭代体系。业务 Agent 提供一个足够具体、可以观察真实状态变化的实验对象，评测系统负责把它的表现拆开看，反过来指导实现。

实现上，我用了 Python、FastAPI、LangGraph、SQLite 和独立的模拟账务服务。调查部分同时保留了固定工作流和模型动态选择工具两种方式，在同一模型和相同业务约束下做对照。后续又补了版本化任务契约、独立试验环境、批量执行、结果与行为评分、表达裁判、案例库和轨迹分析。

我觉得它跟这个岗位比较接近的地方，是我不只关心 Agent 能不能演示成功，也实际处理过评测基础设施里的问题：题目是否可解，评分是否偏向一种路径，失败到底属于模型还是环境，旧结果能不能重新评分，以及修复以后怎样保护原来已经正确的行为。当前场景使用合成数据和模拟退款，没有真实支付上线收益；我会把验证范围讲清楚。

**二、为什么选择账务场景，以及我怎样拆解需求。** 我当时选择这个场景，是因为它能把 Agent 的几个关键问题放在一条完整链路里。用户说“我好像被扣了两次”，这句话本身并没有明确任务参数。系统要理解诉求、寻找相关记录、确认是不是重复付款，还要判断用户指的是哪笔钱，最后才谈得上操作。

这里很容易出现一种情况：回复听起来有道理，但实际业务做错了。比如同一个月有两张不同的账单，每张都只有一笔付款，不能因为金额一样就认定重复收费。反过来，一张账单存在两笔成功付款，其中一笔已经部分退款，也不能再把整笔金额退一次。这样的场景可以用数据库终态检验，适合研究怎么让 Agent 的判断接受外部事实约束。

我先把业务拆成三条线。重复扣费允许进入退款提案和审批；退款进度查询只做读取和解释；订阅价格争议可以说明政策和历史，但涉及补偿或者退差价，需要交给人工决定。先划清这些能力边界，工具和评测预期才有依据，否则模型答得再顺，也可能处理了系统根本没有权限处理的事情。

接着我把业务规则写成规范，再整理成能力和机制矩阵。比如“能调查重复扣费”还太宽，需要继续拆成用户给了账单号、只给付款号、两个编号冲突、完全没有编号，以及多个候选无法确定。故障也要拆：读取失败、审批后条件变化、退款响应丢失、核验暂时不可用，它们的恢复方式并不一样。

这种拆法对我后面的评测很重要。需求不明确的时候，我不会马上让模型生成一大批问题，而是先确认哪些结果是业务允许的，哪些地方还没有规定。规则没有决定的事情，出题模型和评分模型都不应该替业务方拍板。最后形成的任务、实现和评分，才是在回答同一个问题。

**三、整体架构和我的工作边界。** 架构上可以从三层理解。最上面是案件服务，负责身份、用户消息、审批命令、任务入队和状态查询。中间是案件运行时，管理调查图、检查点、证据、预算和执行恢复。下面是独立的 Billing 服务，保存账务数据，通过 HTTP 提供查询和模拟退款接口。

我把应用库和账务库分开，是希望让应用真正面对一个外部系统。调查工具通过 HTTP 读取数据，退款也要经过服务端校验。这样才能构造“外部已经成功、本地却没有收到结果”这种问题。如果所有操作都在同一个函数和同一个内存对象里完成，很多执行一致性的困难根本不会暴露出来。

在 Agent 内部，我把理解、调查和执行拆开。模型可以抽取诉求、决定下一步查什么、询问客户，也可以提交调查结论。退款金额和资格由代码计算，真正的退款请求由图外的执行链路完成。调查工具列表里没有退款写工具，因此不能靠模型随意选择一个工具就直接把退款发出去。

状态不是只有一份聊天记录。案件会保存结构化抽取结果、工具证据、读取次数、澄清次数、提案版本、审批信息，以及已经消费过的命令。这样暂停等待用户或人工以后，恢复时知道自己处于哪个业务阶段，也知道哪些事情已经发生，不能只凭模型重新理解一遍聊天来恢复。

贡献边界我也会主动说明。项目依赖 LangGraph，并使用了固定版本的 langgraph-production 上游组件，检查点、审批账本、执行权账本等基础能力有上游来源。我做的重点是账务业务图、模型协议、目标校验、提案内容绑定、退款发送与核验、独立环境，以及后面的评测和案例闭环。这样面试官如果继续追问，可以直接落到我实际组合和实现的环节。

**四、用一条完整任务把系统串起来。** 我举一个说明性的例子。客户说同一张账单被扣了两次，每次四十九元，希望退掉多扣的钱。系统首先用服务端身份绑定客户，再提取客户给出的编号和诉求，然后读取这张账单的付款记录，确认确实存在两笔成功付款。

接下来还不能立即生成四十九元退款。系统要按付款时间和编号区分原付款与额外付款，再读取额外付款的退款记录。假设这笔钱已经有十七元处于退款处理中，那么这十七元已经占用额度，剩余可退的是三十二元。模型可以说明调查发现了什么，但最终的三千二百分来自确定性计算。

如果目标和金额都满足规则，就生成一个带版本的提案，展示目标付款、金额和依据，等待人工批准。批准之后，系统还会重新检查相关账务状态。假如等待期间又发生了退款，原来三十二元的提案可能已经不适用，就不能拿着旧审批直接执行，需要重新计算并重新审批。

执行时，应用先持久化执行权和发送记录，再通过 HTTP 向 Billing 服务发送一次请求。随后按本次操作的幂等键独立查询结果。只有查到客户、付款、金额和币种都匹配的成功记录，才能把案件标记成确认完成。如果暂时查不到，就保留不确定状态，而不是为了让流程闭环就告诉用户已经退款。

这条链路体现了我的设计顺序：先确认用户要处理什么，再确认事实支持什么，再确认授权覆盖什么，最后确认外部实际发生了什么。每一步都对应独立的问题，也都有可检查的证据。面试时如果只说“加了人审和幂等”，很容易把这些不同层次混在一起，我会用这一条具体任务把它讲清楚。

**五、固定工作流和动态调查究竟比较什么。** 我实现了两种调查方式，主要是想验证一个问题：在这个边界比较清楚的业务里，让模型自由规划工具，是否真的比固定流程更合适。固定组的下一步调查由规则控制，动态组则根据当前消息和证据，由模型选择工具以及结束调查的时机。

需要说明的是，固定组也使用模型做自然语言抽取和结论生成，它不是完全没有大模型的规则程序。两组共享模型接口、客户身份约束、业务工具、金额规则和执行链路。这样比较的重点才是调查决策方式，而不是一组拥有更强工具，另一组缺少必要信息。

固定流程的优势是路径容易解释，调用数量比较可控，业务规则明确时也容易覆盖关键分支。但它的短板同样明显：如果开发时没有想到一种故障或意图组合，规则可能直接走错。动态调查可以根据上下文探索不同路径，有时会发现固定流程漏掉的处理方式，但它也可能提前停止、重复读取，或者在边界问题上反复犹豫。

早期一百道留出题中，固定组通过九十九道，动态组通过九十六道。后来补充新的机制题，第一轮又出现动态组明显高于固定组的情况。这个变化让我认识到，不能脱离题集覆盖讨论哪种范式更好。旧题里的高分，可能只是因为它没有触及固定流程没有实现的分支。

所以我的结论比较具体：在当前账务范围和已经验证的条件下，实验支持选择固定调查作为业务策略，同时保留动态调查用于比较和探索。对于更开放的任务，我不会直接照搬这个结论。要先看任务变化程度、可用工具和错误成本，再通过公平的任务与环境做实验。

**六、模型协议和上下文怎样落到代码里。** 模型层我抽象了统一的调用接口，输入是消息、工具定义和调用配置，输出是统一的回复、工具调用和用量对象。这样真实的 OpenAI 兼容模型、脚本模型和录制回放模型，都可以接到相同业务运行时里。业务代码不用为每种测试方式重新实现一遍。

工具调用的约束有两层。供应商请求里会要求不要并行调用，应用侧仍然自己检查。因为我不能假设模型或者接口一定遵守参数。如果一次返回多个调用，应用不会偷偷选一个执行，而是全部拒绝，并把协议错误反馈回去；纯文本没有工具、未知工具等情况，也有明确处理。

修复机会同样有限。调查阶段最多八次读取、两次澄清、十四次调查模型调用和两次协议修复。这些预算会保存在案件状态里，暂停和重启不会刷新额度。这里十四次只是调查环节的模型预算，不代表整个案件所有模型调用的总数；执行前复核也属于独立阶段，不能和调查读取简单混算。

上下文方面，我同时保留对话和结构化证据。对话说明用户说了什么、模型做了什么；证据记录说明工具实际返回了什么，以及这些内容能支持哪些判断。生成结论时会组织证据包，避免把模型自己之前猜过的话当成已经核实的事实。用户说“上一个客服已经退了”，也必须通过退款记录验证。

这个版本没有做向量记忆、跨案件长期记忆或复杂的上下文摘要压缩。它解决的是有限业务任务里的状态保存、证据组织和有界执行。对我来说，先把这些基础问题做清楚，比为了展示技术栈而加一个没有明确作用的记忆模块更有价值。以后如果任务变长，再根据上下文占用和失败轨迹决定怎么裁剪、压缩和保留关键事实。

**七、目标识别为什么要独立于退款资格。** 这个项目里，我觉得最值得展开的细节，是“这笔钱能不能退”和“用户要退的是不是这笔钱”必须分开判断。早期有一个失败案例，两张账单各有一笔重复付款，客户明确说不要替自己选择，但固定流程找到了第一笔符合退款条件的付款，就直接提出了退款。

那次金额计算合法，模拟审批器也批准了，但业务目标仍然选错了。它说明审批并不能自动弥补调查缺陷，金额规则也不能证明用户意图。后来我专门增加了目标解析这一层，目标需要来自真实客户的指定，或者来自完整候选范围中的唯一额外付款，不能由模型随意挑一笔看起来合理的记录。

具体说，用户点名付款，就先处理这笔付款；如果点名的是原付款，不能擅自替换成另一笔额外付款，而要解释并请求确认。用户只给账单号，就在这张账单范围内找额外付款；存在多个额外付款时，要继续消歧。用户给了账单号和付款号，还需要检查两者是否关联，不能只验证其中一个就结束。

没有任何编号的时候，系统可以在客户账户内调查，但需要覆盖全部候选账单的付款。只有检查完整个范围，且恰好有一个额外付款，才能说目标唯一。如果只看了最新一张账单，碰巧找到一个重复付款，这不构成全账户唯一性的证据。读取预算不足以检查完，就应该保留无法确定，而不是把没看见当作不存在。

另外，完全没给编号和给了一个不存在的编号，是两种不同情况。前者可以通过扫描补充信息，后者需要先让客户核对，不能偷偷换成账户里的另一笔收费。客户在澄清中给出新编号时，也要把它视为更正，不能把新旧编号一起当成两个目标。把这些规则落成代码以后，模型仍然能调查，但目标选择有了可验证的边界。

**八、长程执行怎样处理暂停和后续消息。** 这里的长程主要是业务流程跨越多轮交互和人工等待。一个案件可能正在等客户补充信息，也可能已经生成退款提案、正在等人工批准。等待期间用户又发消息，系统必须判断它是在询问进度、补充信息，还是改变原来的诉求。

比如客户问“现在处理到哪一步了”，这不应该让原来的提案失效。系统可以解释当前状态，继续等待审批。如果客户说“我刚才报错了，是另一张账单”，这就是新的目标证据，需要重新调查，旧提案不能继续使用。如果客户撤回退款请求，也要改变案件状态，不能因为之前已经排过一个任务，就继续按旧意图往下执行。

这些差异在图里通过后续消息处理和明确的状态转移表达，而不是把所有新消息直接拼到提示词后面，让模型自行猜测该如何恢复。命令会先持久化，再进入后台处理；检查点里记录消费过的命令，减少重启后把同一条消息重复应用的风险。

后续覆盖评测还发现一个更细的问题：客户在等待审批时问了一句退款规则，动态组重新调查后只解释了规则，然后把案件结束了，原来的退款诉求丢失。回复本身看起来是正确的，但它没有完成原任务。这说明多轮任务不能只关注最新一句话，还需要保留尚未完成的业务目标。

针对这个问题，后续版本增加了约束：当抽取结果仍包含具体业务诉求时，不能用单纯的政策解释或范围说明替代处理原诉求。已经用历史真实步骤构造测试验证修复逻辑，但归档记录里对应版本还没有完成新的全量实盘回归。所以我会说这个问题已经有代码修复和测试支撑，真实模型稳定性还需要下一轮验证。

**九、审批为什么要绑定具体内容。** 在这个系统里，审批不能只是一个“已批准”的布尔值。因为批准发生时，人工看到的是一个具体提案：退给哪个客户、哪笔付款、多少金额、依据什么证据。如果之后这些内容发生变化，原来的批准不能自动覆盖新的操作。

所以提案会有版本和指纹，绑定客户、付款目标、金额、币种以及相关证据和目标范围。审批令牌与这份提案关联，而且只能使用一次。接口和图内部都会检查版本，过期版本不能通过。这样即使调用方重复提交旧审批，也不会因为案件曾经获批，就执行当前新的提案。

批准后还有执行前复核。因为从提案生成到批准可能隔了一段时间，账务条件有可能变化。比如第三方已经把这笔钱退了一部分，或者账户里出现了另一个需要考虑的候选目标。系统要重新确认业务条件和目标范围，必要时生成新的提案，再走审批。不是任意字段变化都要重新批准，而是判断变化有没有影响当前授权所依据的内容。

金额方面，用整数分存储和计算。已经完成和正在处理的退款都会占用额度，失败退款不占额度；未清算付款即使属于重复扣费，也不能直接退。模型负责解释这些规则和调查结果，金额计算本身放在确定性代码里，执行前再检查一次，避免把自然语言推理作为资金规则的唯一实现。

这个设计也让我区分了三个概念：客户提出请求，是表达意图；人工批准提案，是授予执行权限；账务条件满足，是操作现在仍然合法。三者要同时成立，不能拿其中一个替代另外两个。客户说“领导已经同意了”，仍然只是客户消息，不等于系统里出现了一条有效审批。

**十、接口超时以后，为什么不能直接重试退款。** 我会用一个故障场景解释这个问题：应用向外部服务发送退款，账务服务已经提交事务，但是返回结果的网络响应丢了。应用看到的是超时，可是钱可能已经退了。如果把超时一律理解为失败，重新发起一笔操作，就有重复退款的风险。

我的处理方式是先占用本次批准动作的执行权，持久化发送窗口记录，然后发送一次退款请求。发送之后，无论收到响应还是异常，都通过独立查询核验外部状态。查询到匹配的成功记录，才确认执行完成；查询到持久化的明确拒绝，才确认没有执行。单纯的查无记录、查询超时或者服务不可用，都不能证明原请求一定没有发生。

自动核验最多进行三次。如果仍然无法确认，案件保留为 uncertain，执行记录保持 in_doubt。之后操作员发起恢复，每次只做一次查询，不再发送退款。人工接管也不会清除原来的执行权记录，因为清除以后再执行，反而可能把已经发生过的操作重新做一遍。

这个策略有一个很具体的代价：如果刚写完发送记录，进程就在真正发出 HTTP 请求之前崩溃，恢复时也不会自动补发。这样可以避免不确定窗口里的重复发送，但可能出现实际上没退款、系统却一直等待核验的情况。所以我不会把它描述成通用的分布式恰好一次执行，而是明确说，同一批准动作至多发送一次，并通过外部查询确认结果。

测试也围绕这些窗口做。既检查服务提交后丢响应，也检查发送前和发送后崩溃，还有原请求延迟提交、前几次查询都返回不存在、后续恢复才查到成功的情况。这最后一个例子尤其能说明为什么连续几次没查到，依然不等于确定失败。对这类操作，系统要能诚实表达不知道，同时保留后续核验的条件。

**十一、多层幂等分别防什么重复。** 面试里如果问“不是已经有幂等键了吗”，我会把不同层次拆开讲。第一层是 API 命令。客户端重复提交同一个请求，同一调用人、端点和案件范围内，相同键加相同内容会重放原结果，相同键却换了内容会报冲突，避免一条命令重复进入后台。

第二层是案件和执行恢复。命令先落盘，再返回已受理；运行时记录命令是否已经消费，同时检查执行账本。进程重启后，要知道是调查还没完成，还是已经进入过外部发送窗口。恢复决策不能只看图停在哪个节点，因为外部副作用和图检查点不是同一个事务。

第三层是账务服务。服务端在事务里校验相同幂等键的请求内容是否一致，还通过争议键防止换一个操作键又处理同一件争议。同时检查已有退款和剩余额度，防止两个并发请求分别看到还有余额，合起来却退超了。项目里使用 SQLite 的立即事务，把这些判断和写入放在同一事务边界内。

这几层各有自己的职责。API 键解决重复命令，执行账本解决同一批准动作重复发送，账务请求键解决服务端重复请求，争议和余额约束解决换键以后仍然可能存在的业务重复。不能把它们统一说成“加一个幂等键就全部解决”。

当前业务运行时是每个应用数据库一个执行器，并通过锁限制并发，不是一个跨机器分布式调度系统。评测可以用多个独立 worker 并行跑不同试验，但这也不等于业务端已经支持分布式租约和多副本执行。把这两个并发层次说清楚，才能准确讨论现在的能力以及以后扩展需要补什么。

**十二、怎样把一段用户问题变成可复现的评测任务。** 评测系统是我想重点讲的另一部分。最开始很容易把一条测试理解成一句用户问题加一个标准答案，但对于会调用工具、改变环境的 Agent，这样的信息不够。用户说同一句话，在不同账务世界、不同审批结果和不同故障条件下，正确行为可能完全不同。

因此，我把评测任务设计成一个完整契约。它包含初始账务世界、服务端客户身份、第一条用户消息、客户在追问时可以披露的信息、脚本回答、审批脚本、故障计划，以及达到某种状态后要注入的后续命令。预期部分再规定允许的结论与终态组合、退款目标和金额、必要事实、禁止读取对象，以及表达层需要满足的断言。

比如我要测试“客户没有编号，但通过账户内查询可以定位唯一重复付款”，就需要同时规定初始世界里有几张账单，哪张存在重复，以及客户被问到时确实回答不知道。如果模拟客户其实知道编号，Agent 先问一句就能定位，这道题测到的机制已经变了，不能还按必须扫描账户来评分。

任务还会保存业务规范依据、机制标签、父题和变异方式、数据版本、评分版本，以及是否已经被开发过程看过。冻结时记录任务摘要，并且拒绝直接覆盖原有冻结产物。这样一份报告里的成绩，才能追溯到具体任务内容，避免题目悄悄改了，历史分数却看起来还在同一条曲线上。

我也给任务提供参考抽取和参考工具路径，用脚本模型执行，验证世界、路径与预期能够自洽。这一步不需要消耗真实模型费用，很适合在正式评测前排查数据问题。但它只能证明至少有一条参考路径成立，不能证明题目接受了所有合理解法，这一点是后来真实失败案例让我进一步认识到的。

**十三、冷启动数据怎样扩展，怎样避免只是在改写句子。** 在没有真实线上流量的时候，我先从业务规范和能力矩阵出发，设计种子题，再围绕明确机制扩展。比如对目标识别，可以变化编号披露程度、候选数量和记录关联；对可靠执行，可以变化审批结果、外部响应丢失和核验故障。每种变化都应该能说明它在测试什么。

后续实现了三十个受控变异算子，覆盖表述、多轮对话、业务边界、故障、权限与对抗，生成了一百一十一道覆盖题。这些算子不是随便让模型多写几种问法。每个算子都规定允许改哪些字段、哪些条件必须保持，以及预期结果怎样从业务规则推出。

举例说，只做语言改写时，编号和金额应保持一致；要测试重复付款变成 pending，就得修改对应账务状态，并同步改变关于重复扣费的预期。模型主要负责规定范围内的文本改写，世界状态、故障组合和金额预期由程序按规则构造。这样不会出现模型一边编题、一边凭直觉给答案的情况。

入库前有几道验收。先检查任务结构、账务关系和算子边界，再用独立规则重新校验目标和金额；然后按照结构化语义签名去重，避免把只有措辞不同的题算作新的机制覆盖；再跑参考执行和可解性检查，最后看能力、风险、语言和难度分布，并产生人工抽检材料。这里的去重是结构化签名，不是已经实现了语义向量检索。

这个过程中还发现过一个很具体的工程缺陷：用户把英文编号直接接在中文后面，旧正则使用词边界，结果没有识别出编号。问题并不在大模型，而在确定性目标解析。后来把边界条件改成适合这些编号的 ASCII 字母数字边界，并补了移除修复就会失败的测试。它说明覆盖题除了测语义，也能找到连接自然语言和程序逻辑之间的细小问题。

**十四、评分为什么分成结果和行为，再单独看表达。** 我没有只让一个模型读最终回复、给出总分。因为一句“已经处理好了”并不能证明外部状态真的正确。业务评分首先看结果：结论和案件终态是不是允许的组合，退的是不是指定付款，金额是否正确，账务世界是否只发生允许的变化。

比较数据库时，我做了业务状态投影。随机生成的退款编号和时间戳会造成很多无意义差异，因此比较重点是客户、付款、金额、退款状态等业务字段。允许发生的那笔退款之外，其他记录变化也要检查。如果任务模拟第三方在审批期间新增了一笔退款，这笔外部变化要进入评分基线，不能误认为是 Agent 额外写入。

结果正确以后，还要检查行为。比如做决定前有没有建立必要事实，有没有越权读取，是否按要求澄清，审批记录是否先于发送，是否重复发送，以及是否独立核验。一次碰巧选对目标，不代表过程满足约束。业务通过需要结果和行为都过关，这能区分偶然得到正确答案和有依据地完成任务。

行为评分又不能把工具调用顺序写死。一个真实成功案例里，动态组通过客户范围内的付款列表建立了归属关系，没有像固定组那样单独读取账单，但证据仍然充分。如果要求它完全复制固定流程，就会人为偏向固定组。所以我把必要条件写成事实，并允许同一事实由不同工具结果建立，或者接受几组等价的事实组合。

表达质量另外处理。即使业务状态正确，回复仍然可能把“暂时无法核验”说成“你没有资格退款”，或者把“需要运营决定”说成“已经交给运营处理”。这些问题不能因为数据库正确就忽略，也不能在统计时悄悄混进另一个口径。当前表达裁判独立运行，报告里会说明覆盖范围，业务成功率不直接等于回复质量分。

**十五、模型裁判怎样校准，哪些事情不应该交给它。** 对表达层，我把评分要求拆成原子断言，每次尽量只判断一件事。比如有没有承诺没有依据的到账日期，有没有把尚未核验的退款说成完成，有没有说明补偿需要人工决定。裁判返回真、假或未知，并提供支持判断的回复原文和理由。

能用代码判断的内容，我优先用确定性检查。比如回复出现了任务规定的禁止编号，就把它与客户首句和脚本回答中自己提供的编号作比对。客户自己提到一个编号，系统复述它，和系统从他人数据里泄露一个编号不是同一件事。这样的边界如果全部交给模型打一个笼统分数，后续很难解释争议。

校准中发现过两类有代表性的错误。一类是情态混淆，“这需要运营决定”被读成“已经移交给运营”；另一类是输出长度不足，裁判还没来得及给结构化结果就被截断，最后被记成未知。前者需要收窄断言定义，后者需要检查停止原因和输出预算，不能把两种未知都当成裁判主动表示无法判断。

项目里有四十条回复、一百一十三条断言的校准材料，采用模型预标注，再由用户确认。我不会把它说成多个专家的独立盲标，也不会把分析过的验证条目全部一致，包装成裁判对未知样本有百分之百准确率。裁判与被测模型同源，也可能有相关偏差，这些都决定了表达层目前应该怎样使用。

对我来说，裁判的价值是把大批回复里值得复核的地方组织出来，同时让每一个判定能回到明确断言和文本证据。资金变化、越权读取、审批顺序和重复发送等约束，还是要尽量依靠程序和环境状态检查。这样发生分歧时，能够区分是业务规则、原子断言、模型判断，还是评分输入出了问题。

**十六、批量执行怎样做到隔离、续跑和费用可控。** 每次评测的执行单元是任务、策略组和重复试验编号的组合。不同组合创建独立的应用数据库，载入对应账务世界。多个 worker 用各自的账务服务运行，减少状态和故障计划串到其他试验里的风险。否则前一题退过的钱可能影响后一题，分数就不再只反映当前任务。

我会用固定种子打乱任务顺序，并让两组按试验编号交错运行，尽量减少先跑完一组、再跑另一组时供应商状态变化造成的偏差。普通任务通常重复三次，故障、审批和权限等指定高风险任务重复七次。重复次数不是为了刷出一次成功，而是观察相同任务在多次执行中的波动。

费用方面，多个进程共享一个花费账本，调用前预留预算，调用后按实际返回的用量和配置价格结算。账本通过事务协调并发，避免每个 worker 都以为自己还有全部预算。但预留的输入 token 来自字符数估算，不是严格的计费上界，所以我会把它说成预算控制机制，而不是数学上绝不会超出一分钱的保证。

结果按试验逐条写入并刷新，重新启动套件时可以跳过已经记录完成的组合。这里要区分已完成试验级的续跑和任意中断点恢复：当前实现并不是把一个跑到一半的动态对话无条件接着跑，残留数据库也不能随意覆盖。业务案件的恢复和评测套件的续跑，是两个相关但不同的问题。

供应商故障也要有停止条件。后续版本会根据异常类型和 HTTP 状态识别一类模型基础设施故障，连续达到阈值就停止继续消耗时间。单个试验还会保留错误来源和原始产物，避免把所有异常压成一个零分。当前配置一致性校验仍有扩展空间，未来接更多运行协议时，需要把超时、工具能力和完整配置摘要一起纳入恢复检查。

**十七、实验结果怎样讲才经得住追问。** 如果让我选几组结果讲，我会按照它们回答的问题来组织。第一组是早期正式对照，一百道留出题、两种策略各跑一次，共两百次真实模型运行。固定组九十九次通过，动态组九十六次通过，总模型费用约零点四四美元。这说明在那一批任务上，没有看到动态调查带来优势，但不能由此推断两种策略在所有业务上有固定优劣。

第二组是补充机制以后的评测。四十八道任务里，二十四道各跑三次，另外二十四道风险任务各跑七次，每组二百四十次。首轮固定组的任务等权成功率大约百分之七十点一，动态组大约百分之八十八点六。新机制把固定规则遗漏的读取故障和意图分支暴露出来，也说明早期高分不代表覆盖完整。

随后在同一批已经曝光的题上定位问题、修改实现，再做回归，固定组达到百分之九十五点一四，动态组为百分之八十七点五。固定组提升大约二十五个百分点，是这一批回归的观察结果，改动包含规则、抽取定义和提示词等多个部分，不能全部归功于某一句提示词，也不能当作未见任务的泛化提升。

这里有个容易被问到的统计细节：固定组是二百二十五次通过，除以二百四十，得到百分之九十三点七五，为什么报告是百分之九十五点一四？因为主指标先算每一道任务的通过比例，再对任务等权平均。高风险题多跑几次，是为了看稳定性，不能因此让它自动在整体分数里获得更大权重。

同一回归批次里，固定组和动态组平均模型费用分别约零点零零一六四和零点零零五一三美元，百分之九十五分位运行时延约十一点二秒和四十六点四秒。固定组费用低约百分之六十八，尾延迟低约百分之七十六。不过这个时延是案件运行时加账务 HTTP 的范围，没有真实人工审批等待；这批业务成绩也没有包含新一轮完整表达裁判结果。数字有用，但要把分母、范围和版本一起讲出来。

**十八、指标和门禁为什么不能只看一个平均分。** Agent 评测里，平均成功率只能回答一部分问题。比如两个版本都平均通过九成，一个是在每道题上偶尔失败，另一个是某一类权限任务始终失败，它们的风险完全不同。所以报告除了总体指标，还要按业务线、机制、语言和风险切片，并把安全事件单独列出来。

重复试验也有不同看法。前三次里至少一次成功，反映的是是否有机会做对；前三次全部成功，反映的是在这几次观测里是否稳定。项目里会展示这两类统计，但不会拿“多试几次总能成功”代替正常业务流程的可靠性。用户通常不会愿意为了同一个账务问题反复尝试，直到某次碰巧处理正确。

对于未知或者缺失结果，我会同时计算上下界。把未知都当失败，是保守下界；把未知都当成功，是乐观上界。它们表示未完成判断对成绩的影响，不是统计置信区间。如果连上界都达不到工程阈值，可以判不通过；下界已经达到且其他约束满足，才有条件通过；卡在中间就应该标记结论不足。

门禁还包括总体和业务切片阈值，以及必须通过的回归任务。确认发生未授权操作、错目标、超额、重复写入或跨客户等安全违规时，不应该让其他大量简单成功把它平均掉。当前实现是离线的发布检查命令，可以表达这些判断，还没有连接到企业真实发布系统，不能直接说已经实现生产自动发布门禁。

还有一个重要边界是数据曝光。一份最初封存的题库，一旦被我拿来查看失败、分析并修复，就已经成为曝光回归集。即使工具输出通过，语义上也只是这批已知题达到门槛。要支持新版本对未知场景的判断，还需要新的封存任务和独立复核，这个状态必须跟着数据一起记录。

**十九、一个完整的失败案例怎样从现象走到修复。** 我会优先讲“客户不知道编号，动态 Agent 提前结束”这个例子，因为它能体现我如何看轨迹。用户希望处理重复扣费，但答不上账单号。旧版本查了账单列表，向用户问了一次，听到不知道就以信息不足结束。单看最终回复，好像也有理由，因为用户确实没给信息。

但我展开轨迹以后发现，它只用了八次读取预算中的一次，还有大量调查机会。账户里的账单和付款是可以查询的，因此问题不在工具缺失，也不在预算耗尽，而在把“用户不知道”错误地等同于“系统无法继续定位”。旧提示和退出条件能解释这种提前停止，不过我没有做只改这一项的独立消融，所以不会把原因说得比证据更强。

修复时我没有简单要求模型“多查几次”，而是把能结束调查的条件写清楚。没有编号，可以在预算内扫描候选；完整范围内只有一笔额外付款，才可以自动定位；存在多个候选，需要询问客户；预算不够覆盖候选，就保留不确定。动态组提前提案而证据不完整时，代码会反馈缺少哪部分调查范围，并消耗已有的修复预算。

验证也不只回放原来那一句话。我补了唯一重复、多个重复、完全没有重复，以及预算不足几类对照。这样能观察修复是不是从“过早放弃”走向另一个错误，比如为了完成任务随意选目标。原来三条同类失败在定向复测中通过，但当时每题每组只跑一次，所以这是修复方向有效的证据，还不能代表已经充分证明稳定性。

这个案例让我形成了一个比较固定的排查顺序：先还原用户目标，再看第一处偏离发生在哪里，然后检查当时还剩什么信息、工具和预算，最后再提出改动。不能看到最终失败，就直接增加提示词。先找清楚缺的是能力、规则、信息还是执行机会，修复才比较容易被验证。

**二十、为什么成功案例和相邻意图同样值得深挖。** 另一个让我印象比较深的迭代，是订阅退款意图。用户说“把涨价的差额退回来”，旧系统有时只解释价格政策；用户说取消后希望退未使用周期的费用，又可能被识别成查询已有退款状态。两种情况下，回复都在谈退款，但处理的业务不是用户真正提出的那一件事。

后来我把“正在申请新的退款或补偿”和“查询已经存在的退款”分开表达，调整抽取字段和路由优先级。订阅上的新补偿诉求，要读取历史与政策，再交由人工决定；只问退款什么时候到账，就应该查询已有记录。问题是定义稍微放宽，又可能把普通查询一起升级，所以还要补相邻意图的反例。

权限防护也遇到过类似问题。加强跨账户请求识别以后，用户为自己的请求说“主管已经批准，别再检查”，有时也被当成操作他人账户，正常请求全部转人工。正确处理应该是区分目标账户和授权宣称：真正跨账户的请求不能处理；本人请求里伪造的批准，只需要忽略这个宣称，继续调查并等待系统里的真实审批。

这就是我为什么单独保存成功案例。成功案例不只是用于展示系统不错，而是在描述哪些行为必须被保护。比如付款列表已经能建立归属的合法替代路径、客户只询问价格原因、本人正常请求附带错误授权宣称。这些对照能阻止修复越来越保守，最后通过一律拒绝和升级得到看似安全的分数。

案例库会把任务、试验、失败发现、人工复核意见、修复版本和回归结果关联起来。失败可以按检查项聚类，成功样本也会按业务和语言抽样。晋升回归目前是状态和关联管理，不是自动生成一条已经验收的新题。这里的闭环是案例推动规则、提示和评测改进，没有在后台自动训练模型权重。

**二十一、最新覆盖评测里，环境错误和题目错误怎样处理。** 后续一轮覆盖评测使用了一百一十一道任务、三十种变异算子，共运行一千零二十六次试验，四个 worker，约五十三分钟，模型费用约二点八三美元。这个阶段最有价值的收获，不只是得到了更大的样本量，还发现了评测系统本身会怎样产生误导。

其中一次是模型服务返回余额不足，影响了五十次试验。有些动态组试验因此失败，但固定组还有一部分通过正则抽取和兜底回复完成了。假如只看业务终态，就会把供应商不可用时的兜底能力算成真实模型成功，对两组的比较很不公平。后来按模型错误事件和状态信息，把这批受影响结果单独改判为基础设施未知，并保留原始结果。

改判后，固定组是四百八十三次通过、六次失败、二十四次未知；动态组是四百五十四次通过、三十三次失败、二十六次未知。报告中已判定部分的任务等权指标，不能直接当作完整一千零二十六次的总体成功率，更不能把未知静默删除。当前也不是所有超时都算外部故障，运行器自身超时与供应商错误仍需要分别判断。

固定组那六次失败，后来定位为两道任务的预期问题。题目想测试用户不知道编号时的全账户扫描，却允许模拟用户在澄清时给出编号。Agent 先问、拿到编号、再查询，是合法路径，评分却只接受扫描。修正时把客户可披露信息与原本要测的机制对齐，升级数据版本，并在验收中增加路径一致性检查。

因为这里改变了模拟用户能说什么，任务环境已经改变，不能拿旧轨迹换一个标签就宣称新版通过。需要重新执行。与之不同，如果环境不变、只是评分规则修正，可以保留原产物另做重评分。分清这两种情况很关键，否则 Agent 修复、评分修复和题目修改会全部混成一条虚假的能力提升曲线。

**二十二、Trace、回放和前缀诊断各自解决什么问题。** 观测上，我首先把本地事件、证据和执行账本作为事实记录，再把模型调用、工具调用以及审批和核验等事件关联到 Langfuse。这样可以从一个案件追到多次执行和恢复，看到某个结论之前发生了哪些读取，也能对照费用、模型耗时和整体运行时延。

这里我区分本地已经记录和云端已经收到。把事件交给 SDK，并不代表服务端一定能查询到。已有批次确实出现过并发投递缺失：七百七十四次试验中，有六十二条轨迹在服务端查不到。因此状态要如实标记，并通过服务端读回验收，不能仅因为调用上传接口没有抛异常，就宣称全部 Trace 已经完整归档。

本地评测产物还会保存消息、工具证据、案件事件和完整账务终态。旧批次曾经没有保存完整终态，后来即使想用更严格的规则重评分，也不能靠初始世界和一张回执推算缺失信息。我的处理是保留原成绩，同时明确哪些检查只能沿用历史结果，哪些因为证据不足无法重新认证。

回放也有不同用途。模型响应录制回放，适合固定调用序列来检查工程行为；只读前缀诊断，则是在真实环境执行已记录的调查工具步骤，逐项核对返回，再观察后续处理。遇到返回不一致，必须标记无法复现，不能一边使用旧证据一边假装还处在原来的环境。

当前前缀诊断只支持审批和写入之前的只读调查，并不支持任意故障计划或外部写操作快照恢复。诊断后缀的成绩也不并入端到端主分数，因为前面已经人为提供了一段轨迹。它适合帮助定位问题出在前段调查还是后段决策，不能当作系统从头独立解决任务的能力。

**二十三、接入外部 Benchmark 时，我实际遇到了什么。** 我做过一轮独立的 τ Retail 接入试跑，固定上游提交、任务子集和运行配置，使用官方 Agent 与官方用户模拟器，执行前五道任务，每题一次，结果四道通过。Agent、用户模拟器和自然语言裁判都配置为项目使用的 deepseek-flash，所以这只是特定配置的接入结果，不能直接和默认榜单比较。

这一轮也不是 BillingOps Agent 在零售场景下取得的成绩，因为还没有把自己的调查流程适配到零售工具域。我实际完成的是跑通独立环境、固定配置、整理产物，并对失败轨迹做分析。把这件事说明白，才能证明我知道 Benchmark 接入和被测系统迁移是两项不同的工作。

失败题很有代表性。Agent 已经找到要换的商品，计算了五美分差价，并向用户请求确认。模拟用户在同一条消息里表示同意，又输出了停止标记，于是环境结束，没有再给 Agent 一个执行修改工具的回合。最终数据库评分失败，自然语言评分通过。只看总分，很容易得出 Agent 不会执行修改的结论，但轨迹说明首先消失的是执行机会。

我没有因此删除这道题或改成成功，而是保留零分和终止原因，把问题归入模拟用户结束协议的分析。它给我的启发是，用户同意不等于任务完成，模拟器应该允许系统完成后续写入和核验。Agent 评测除了被测模型，还依赖用户模拟器、环境和终止条件，这些都可能影响结果。

另外，接入时还发现固定版本任务的实际评分依据与文档描述存在差异，所以以任务配置和真实评分分解为准；SDK 返回费用为零，也可能只是没有识别模型价格，不能当作免费。外部接入对我来说不是把命令跑起来就结束，还要核对环境、评分、终止、费用和版本，确认每个数字到底代表什么。

**二十四、如果接手岗位里的统一 Harness 层，我会怎样推进。** 当前项目已经统一了模型调用接口，但我不会把它说成统一适配了 Claude Code、Codex 和 OpenCode。这两层不一样。模型接口主要处理消息、工具定义和返回格式；一个完整 Agent Harness 还可能自己管理文件、终端、上下文、权限、子进程和恢复，因此需要更大的运行协议。

如果由我继续做，我会先用一个小的纵向闭环定义边界：选一个固定版本的任务集和两个 Harness，能够准备环境、启动任务、收集事件、判断终止、归档产物，并调用任务自己的评分器。先验证一题从头到尾可以复现，再扩到批量执行，避免接口抽象很齐全，但始终没有真实任务能完整跑通。

接口上，我会把任务、环境、运行适配器和评分器分开。任务定义输入、资源和预期；环境负责创建、重置和清理；适配器负责把任务交给指定 Harness，收集状态和事件；评分器根据环境终态与任务规则判断结果。公共事件可以表达模型调用、工具开始结束、文件产物、退出和错误，同时保留 Harness 原始事件，避免统一格式丢失诊断信息。

公平性也要明确选择比较对象。如果比较的是完整产品系统，就应该允许各自原生能力参与，但在报告里记录差异；如果想比较模型本身，就要尽量控制工具、提示、环境和预算。两种实验不能混成一张没有说明的排行榜。依赖版本、上下文限制、网络权限和超时同样需要冻结，因为它们都会影响任务能否完成。

SWE-bench、Terminal-Bench、GAIA 等接入也应该保留各自任务和评分语义，统一生命周期与产物协议。当前我还没有把这些全部接入；我能迁移的是已经处理过的任务冻结、环境隔离、重复试验、错误分类、状态评分和案例归因方法。后续若扩大到容器和集群调度，再补镜像、资源配额、取消清理和故障恢复，不把这些规划写成现有成绩。

**二十五、这个项目怎样对应 DevOps Agent 和工程实践。** 如果把场景换成内部研发助手，我认为可迁移的是控制外部操作与验证结果的方法。比如代码修改可以在隔离工作区里进行，测试结果要以实际退出和产物为依据；涉及部署或其他高影响操作，要明确批准对应哪份变更，超时以后要查询真实状态，不能因为 Agent 最后一条消息说完成了就认定成功。

不过具体操作的恢复策略要重新设计，不能把退款的至多一次发送机械搬到所有 DevOps 工具上。有的读取可以重试，有的构建可以重新执行，有的发布操作需要查询版本和部署状态，还有的操作要靠平台自身的幂等接口。共同点是先识别副作用和外部事实，再决定重试、补偿还是人工处理。

在评测上，也可以沿用任务世界的思路：固定初始代码、问题描述、运行环境、可访问材料和工具权限，最后检查测试、文件变化或服务状态。技术答疑如果只是回答正确，却引用了不存在的日志，仍然有证据问题；部署任务如果进程启动了，但健康检查没有通过，也不能只按终端输出的某句成功提示评分。

现有工程验证主要依靠测试代码、故障注入、参考执行、脚本模型和真实模型小批次复测分层进行。规则、金额、审批版本和恢复窗口适合确定性测试；自然语言意图和动态选择则需要真实模型验证。已有记录里的测试通过，只支持对应版本和范围，不能用脚本模型通过去证明真实模型已经修好，也不能把检查过源码说成刚刚重新跑过全量测试。

对于 AI Coding 工具，我会强调自己能够理解和验证生成的改动：先说清状态约束和失败样例，再把任务拆小，检查修改是否触及正确模块，最后用能暴露原问题的测试和回归判断。面试时具体用了哪款工具、哪些修改由我主导，我会按实际经历回答；不会因为岗位列了几个工具名字，就把未完成的 Harness 适配说成自己的经验。

**二十六、我会怎样收住这个项目，以及继续做什么。** 如果让我概括这个项目里最大的收获，我会说是学会把一次 Agent 成功拆成多个能够独立验证的问题：用户目标有没有识别对，证据有没有查充分，授权有没有覆盖当前操作，外部状态有没有真的改变，最后的回复有没有准确表达结果。把这些层次分开以后，很多原来模糊的失败就能落到具体环节。

第二个收获是，评测本身也需要被验证。参考执行通过，未必覆盖了所有合法路径；模型裁判给了答案，未必正确理解了断言；运行环境暂时坏了，不能直接算成 Agent 能力下降。真正可复用的评测设施，需要保存足够证据，让评分、环境和 Agent 都能被检查，而不是只有一张成功率表。

如果继续推进，我会优先完成当前修复版本的真实模型回归，把尚未解决的动态调查读取效率、协议不稳定和多目标澄清问题逐项验证，再建立新的未曝光任务和表达校准材料。同时补齐并发追踪投递、配置冻结以及中断试验处理。等本域的执行和数据契约稳定，再扩到更多 Benchmark 和 Harness。

我希望在这个岗位上继续做的，就是把这些经验放到更通用的平台里：让不同 Agent 能在可复现的环境下运行，让指标能够解释，让失败能够定位，让每次修复都能通过独立证据验证。BillingOps 的业务范围还比较小，但我已经在一个完整场景里经历了从实现、实验、发现问题到修正评测和回归的过程，这也是我最愿意在面试里展开讨论的部分。
