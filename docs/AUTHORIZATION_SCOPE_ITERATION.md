# 退款授权范围：双 Loop 案例挖掘与修复

本轮针对会话中发现的“三笔付款、两笔多扣、客户只要求退其中一笔”问题，完成 Agent 修复、评测修复和开发回归资产补充。它同时触发两个 Loop，不能只归因于模型，也不能只增加几条数据就算修好。

## 归因方法

依据[美团 Agent 评测白皮书](https://tech.meituan.com/2026/09/10/Agent-Evaluation-White-Paper-01.html)，先核验任务、环境与评分标准，再用固定评测条件检查 Agent；评测修正带来的分数变化不能记成 Agent 提升。依据[冷启动评测集文章](https://brenchcc.github.io/Awesome-LLM-Research-Collections/notes/zh/agents/cold-start-agent-evaluation-dataset.html#合成后必须经过四道验收)，新增资产经过语义去重、独立规则校验、参考可解性和分布检查。两篇文章读取于 2026-10-12。

| 挖掘出的 Case / 现象 | 证据和归因 | 本轮处理 |
|---|---|---|
| `PAY-2和PAY-3都重复了，但只退PAY-2` | 原代码把原文出现的付款号全部当成授权对象；旧 32 题和 128 题有单笔限制、整单多退，却没有“多个付款号＋范围限制”的字面组合 | **Agent Loop + 评测 Loop**：修解析并加入交叉场景 |
| `不要退PAY-2，只退PAY-3` | 否定对象混进正向目标；仅有单笔金额与整单余额检查无法识别此越界 | **Agent Loop + 评测 Loop**：分别记录正向、排除、背景目标 |
| `只退其中一笔`，尚未选择 | 原实现可能受模型 role 影响计算全部退款，或仅靠金额阶段失败 | **Agent Loop + 评测 Loop**：保留数量限制，实际暂停澄清；未选目标不得形成提案 |
| 错提案尚未执行 / 越界发送被账务拒绝 | 只检查最终退款会漏掉前面的错误；零新增退款不能证明是哪层拦住 | **评测 Loop**：分别评分提案、发送尝试、实际新增退款 |
| 客户只说普通“确认” | 模拟客户若对任意更大范围都说是，会替 Agent 扩授权 | **Agent Loop + 评测 Loop**：原限制持久化；模拟器依据公开客户限制检查当前对象和金额 |
| 审批前把 PAY-2 改成 PAY-3 | 仅看最终 PAY-3 退款正确，会漏掉“修改消息从未投递却提前退了 PAY-3” | **评测 Loop**：未来消息只由预定 followup 投递；检查修改消息消费、旧提案失效、新版本和新审批 |
| PAY-2 已全退，PAY-3 仍有余额 | 客户授权的目标已无余额，不得自行改退 PAY-3；“整单已无多扣”的旧评分条件也不适用 | **评测 Loop 补覆盖/标准**：以明确目标余额判定正确零写结果，保留其余证据要求 |

旧资产的覆盖统计是可重复的字面筛查，不能证明所有自然语言边界都已穷尽。新增 Case 的期望由本次代码助手显式编写，再由独立账务 oracle 校验；没有使用待测授权解析器生成标准答案，也没有声称已完成独立人工审核。

## Agent 修复

`investigation/authorization.py` 从客户原文建立授权约束：选择的付款、明确排除的付款、仅作背景的付款、最大笔数、是否仍需澄清及来源命令。模型提供的 locator/exclusive 标签不能扩大明确的原文指令。

`target.py` 与 `b1.py` 将定位线索和执行目标分开。三笔各 100 元、应付 100 元的账单仍会查全账务证据，但“只退 PAY-2”仅产生 PAY-2 的 100 元退款。另有 100 元多扣不等于本次获得了处理授权。数量明确而对象未选时进入真实澄清；指定付款已退完时不替换目标。

`state.py` 和 `graph.py` 按实际命令顺序保存授权话语，避免“审批后修改→再次澄清”被旧 extra_info 覆盖。普通确认不能抹去限制。真正的目标修改继续使用既有版本机制，作废旧提案/审批并重新审批；授权约束也进入证据摘要，在执行前复核。

适用范围为 B1/B2 动态流程。冻结的 B0/legacy targeting 与发送后只查证的恢复策略保持原有语义。解析器支持有限的直接指令语法；识别到但不能可靠绑定的限制会保守澄清，不声称能理解任意自然语言。

## 评测修复

`v2_scoring.py` 的 `business-v2-trace-1.3` 使用独立 `author_scope` 检查静态明确付款授权。Agent 自己提取的目标、提案内自报授权、普通确认和操作员批准，都不能反向修改 GT。

| 观察到的事实 | 评分含义 |
|---|---|
| 提案有 PAY-3，但客户只授权 PAY-2，尚无发送 | 行为失败；记录错误提案，不宣称实际越权退款 |
| 已尝试发送 PAY-3，但没有新增退款 | 越权尝试事件；保留拒绝或未知证据，不等同于实际出款 |
| 独立账务终态新增 PAY-3 退款 | 实际范围越界，即使总额没有超过整单超收额度 |
| 轨迹或前后账务快照缺失 | 保留 unknown，不能据此断言“未发生” |

动态目标更改不能拿最终授权追溯判早期合法提案错误。AS12/AS13 另外要求预定客户消息真实消费；AS13 必须体现旧范围失效和新审批。此专用检查不是一个已覆盖所有多轮自然语言的通用时序 oracle。

`v2_controls.py` 的 `v2-controls-1.7` 新增可选公开 `confirmation_scope`，核对当前确认问题中的付款对象、金额和币种。未来诉求不提前放入模拟客户的已知事实。操作员模拟器仍然批准实际产生的提案，不读取隐藏答案替 Agent 筛掉错误。

`v2_runner.py` 的 `v2-runner-1.7` 注册独立的 `authorization-scope-v1` suite，使用自身 Case ID、风险与暴露元数据。原有 32/128 题、历史 runs 与历史结果没有重新标分或覆盖。

## 资产与证据

最终验证（2026-10-12）：全套 **963 项测试通过**；14 个 Case 的同条件范围回放包含 **42 个 role/轮次检查，旧实现匹配 13 个，修复后匹配 42 个**。这是授权代码的确定性回归结果，不是模型任务成功率。真实图、消息消费与新审批链测试通过；未调用真实模型或真实支付服务。

- [新增资产](../data/tasks/authorization-scope-v1.json)：14 条用例、11 个语义场景、3 条同场景语言变体。包含正向单笔、背景多付款号、否定、英语、未选单笔、凭证定位、合法两笔、目标已退款、仅查询、普通确认、多轮更改、跨客户权限。
- [四道验收](../analysis/authorization-scope-v1/admission.json)：语义分组、独立规则、真实本地 Billing HTTP 参考及分布清单。
- [参考执行细节](../analysis/authorization-scope-v1/reference/report.json)：9 个退款正例、5 个零写负例；共 11 次参考 POST，并用独立回执及账务终态核验。
- [同条件范围回放](../analysis/authorization-scope-v1/replay.json)：保存原始输入、独立期望、旧/新输出及源文件摘要。
- [统一测试记录](../analysis/authorization-scope-v1/verification.json)：本轮最终 pytest 结果和代码摘要。

四道验收中的参考可解性仅证明 fixture、账务接口和给定授权下的目标结果可行。它不执行模型、客户对话或人工审批，也不是“所有 Agent grader 都已通过”的 Gold 认证。AS12/AS13 的交互另外由真实图执行回归验证。数据均为已暴露的开发合成 challenge，风险刻意过采样，不能据此估算生产发生率。

复现时使用新的输出路径，保留旧报告：

```sh
.venv/bin/python scripts/check_authorization_cases.py --reference --out /tmp/authorization-admission-new.json
.venv/bin/python scripts/replay_authorization_scope.py --out /tmp/authorization-replay-new.json
.venv/bin/python -m pytest -q
```

确定性范围回放在固定账务事实与模型提取标签下比较旧/新代码，不调用真实模型、不审批、不退款。42 个检查含同 Case 的不同 role 和对话轮次，不能当作 42 个独立场景，更不能当作模型成功率。真实模型端到端实验仍需独立注册、固定模型与评测版本，并保留未知结果。

本轮没有实现跨案件的“处理中争议占用/自动关联原案”；这是与授权范围解析不同的待补能力。也未新增账单额度预留机制或改变实际执行的幂等与查证边界。
