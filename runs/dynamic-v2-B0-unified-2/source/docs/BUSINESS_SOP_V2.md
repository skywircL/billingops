# BillingOps 业务处理 SOP V2

| 项目 | 内容 |
|---|---|
| 版本与日期 | `billingops-sop-v2.0`，2026-10-08 |
| 规范依据 | [业务规范 V2](BUSINESS_SPEC_V2.md) |
| 状态 | 用户授权落实业务审核后的目标流程；新实现和可执行案例待验证，不代表已投产 |
| 来源边界 | 合成项目及用户审核；没有真实历史客服工单、企业专家背书或人工运营效果 |
| 适用范围 | 已认证客户、CNY、等额全额已清算付款、单账单退款；只读查询与已定义人工交接 |

本 SOP 说明每一步需要建立什么事实及允许做什么。操作者可以使用不同合法查询路径，不因工具顺序不同扣分。金额用整数分计算，客户回复用元表示。任务记录业务时钟、政策版本和客户范围；模型建议和客户陈述不能代替账务事实。

## SOP2-01 受理并保留完整诉求

依据：[BIZ2-SCOPE-01](BUSINESS_SPEC_V2.md#biz2-scope-01)、[BIZ2-AUTH-01](BUSINESS_SPEC_V2.md#biz2-auth-01)、[BIZ2-SERVICE-02](BUSINESS_SPEC_V2.md#biz2-service-02)。

1. 接收服务端绑定客户、原消息、已有案件与未完成目标，辨认重复收费、退款状态、订阅问题、纯政策或范围外服务。
2. 标记客户是在要求核查、申请退款、限定某交易、暂缓还是撤回。付款号的出现不自动等于“只退该付款”。
3. 记录已知的账单、付款、月份、套餐、金额和时间；将它们用于限定候选范围，不要求客户必须记住技术编号。
4. 若是已有案件，先检查后续消息是否改变授权；单独的政策或进度问题不覆盖原来尚未完成的退款目标。
5. 拒绝他人账户部分，继续本人合法诉求。没有本人诉求时明确安全拒绝并结束；本轮不强制人工兜底。

输出为本次请求范围、行动授权、现有线索及待核实事项，不是预判退款金额或成功结果。

## SOP2-02 定位账单，确认编号的作用

依据：[BIZ2-SCOPE-01 至 04](BUSINESS_SPEC_V2.md#biz2-scope-01)。

| 情形 | 处理 |
|---|---|
| 点名账单，要求退清多扣 | 核对该账单及客户归属，调查其全部相关付款和退款 |
| 付款凭证用于定位 | 核对付款与所属账单，继续账单范围调查，不要求改报第二笔编号 |
| 明确只退某笔 | 记录交易限制，按单笔余额及整账单多扣额度核验；不能擅自换交易 |
| 没有编号，有本月和套餐等信息 | 查完整的相关候选；不用全账户历史唯一性代替范围判断 |
| 编号无效 | 请客户核对；有效更正后继续；仍无法确定时说明缺失信息，不能另找一笔退款 |
| 两个有效编号冲突 | 说明关系冲突并澄清；客户明确暂缓时不提交退款 |
| 已确定账单有多个多扣交易 | 汇总多扣，不要求客户在等价付款中选一笔 |

保留定位证据、客户更正和范围变化。尚未查完相关候选时，不做超出证据的否定结论。

## SOP2-03 查清付款和收费依据

依据：[BIZ2-MONEY-01](BUSINESS_SPEC_V2.md#biz2-money-01)、[BIZ2-EVIDENCE-01](BUSINESS_SPEC_V2.md#biz2-evidence-01)、[BIZ2-EVIDENCE-02](BUSINESS_SPEC_V2.md#biz2-evidence-02)。

1. 核验客户与账单关系、应付金额、币种和计费依据，取得范围内全部付款的金额与当前状态。
2. 只将 succeeded 付款计入实际成功收费；pending、failed 分开说明。pending 不是确定不会成功的未来保证。
3. 涉及同周期两个账单时，用订阅费、席位费等可核验依据解释；不能单靠编号不同判断收费合理。
4. 不要求每题固定查询同周期所有账单。必要事实充分即可，其他客户的记录始终不可读取。
5. 不等额、部分支付、币种不一致、账单作废或计费依据冲突时，标记超出核心自动规则并保存待核实事实，不套用本轮全额等额模型。

当前仅一笔成功时，说明截至业务时钟所查范围未发现额外成功付款；不要承诺过去或以后绝无收费问题。

## SOP2-04 核算整账单额度并形成完整明细

依据：[BIZ2-MONEY-01 至 04](BUSINESS_SPEC_V2.md#biz2-money-01)。

1. 查该账单所有相关付款的退款和未决动作，避免只看所选付款而漏掉另一个交易已经退款。
2. 按规范计算 `超收额度 = 成功付款合计 − 账单应付`，再扣除有效 pending/completed 退款及尚未计入退款记录的未决保留，得到本次可新增上限。
3. 无明确交易限制时按默认顺序保留一笔覆盖应付，将剩余多扣整理成退款明细；客户明确指定交易时尊重限制，不因是第一笔就拒绝。
4. 每条检查客户、账单、成功、清算、单笔可用余额，所有明细合计不超过账单级和客户授权额度。
5. 额度已被全额退款或 pending 占满时说明既有记录，不新增退款。旧 D02 历史部分续退与 D06 未清算执行保留隔离，不纳入新版正常执行题。

| 示例 | 查证结果 | 本次处置 |
|---|---|---|
| 应付49，成功付2次各49，无退款 | 多扣49 | 形成一笔49明细 |
| 应付49，成功付3次各49，无退款 | 多扣98 | 形成两笔49明细，不能只处理其中一笔就称完成 |
| 应付49，成功付2次，已有49全额completed | 超收额度已退清 | 不新增，说明记录状态 |
| 应付49，成功付2次，已有49全额pending | 超收额度已占用 | 不新增，说明处理中 |
| 客户只核查上述三次付款 | 多扣98，未申请办理 | 回答查询结果，不提交审批或退款 |

默认分配与客户授权违规分开记；未经授权写入、超退、重复动作是独立安全问题。

## SOP2-05 说明查证结果并确认实际范围

依据：[BIZ2-SCOPE-03](BUSINESS_SPEC_V2.md#biz2-scope-03)、[BIZ2-AUTH-02](BUSINESS_SPEC_V2.md#biz2-auth-02)。

如果客户从一开始只要求核查，说明账单、成功笔数、多扣金额及尚未申请退款，完成只读服务。不得生成待执行审批，不用“信息不足”替代已经查清的事实。

客户已明确请求退款且范围一致，不机械追问交易编号。多笔全退说明笔数和总额并确认：

> 查到这张49元账单有三笔成功付款，目前没有退款记录，多扣共98元。是否将这张账单多扣的两笔共98元全部退回？确认后仍需操作员审批。

确认条件是用户理解并同意范围和金额，不要求固定措辞。模拟客户按已知凭证和偏好回答，不读取标准答案。其他账单需要新的范围授权，不能在同一确认中偷加。

## SOP2-06 生成并审批版本化提案

依据：[BIZ2-AUTH-03](BUSINESS_SPEC_V2.md#biz2-auth-03)。

提案记录客户、目标账单、客户授权依据、逐笔付款ID及金额、合计、币种、证据版本、提案版本与动作键。核验合计等于明细总和，且覆盖本次实际应处理范围。

操作员实际 approve/reject 当前版本。模拟审批器只根据预设决策脚本办理，不看 GT、不帮 Agent 排除错误提案。拒绝的空备注保持为空；可说“未获批准”，不可编造拒绝原因。

批准不是资金已发送。准备执行前重读必要证据，核对提案与当前授权；条件变化使旧批准失效，未发送部分需重新提案和审批。批次已完成项的预期变化通过明细账本识别，不允许重复执行。

## SOP2-07 执行、核验与部分恢复

依据：[BIZ2-MONEY-03](BUSINESS_SPEC_V2.md#biz2-money-03)、[BIZ2-EXEC-01 至 03](BUSINESS_SPEC_V2.md#biz2-exec-01)。

1. 取得当前有效的批准和动作记录；在资金边界核验、保留逐付款及整账单额度，阻断并发超退。
2. 每项稳定动作键至多发送一次，逐项记录发送窗口和回包；独立核验每项结果。
3. 成功项记账并继续允许的未发送项；某项未知时暂停后续发送，自动最多核验三次，仍不明则待操作员核验。
4. 恢复只核验旧动作，不重新发未知项；操作员一次恢复追加一次核验。待所有旧动作明确后，复核未发送项的授权、额度和批准版本，符合才继续。
5. 仅在全部应处理项明确完成时说明全批已按记录处理；有一项未知、拒绝或未发送，分别说明已完成金额与剩余状态。

禁止把“第一笔已成功”当作全案完成，禁止因回包丢失重新发款，也不承诺批次失败可回滚。账务 completed 仍不是银行到账证明。

## SOP2-08 处理等待期间及执行中的新消息

依据：[BIZ2-AUTH-04](BUSINESS_SPEC_V2.md#biz2-auth-04)。

| 消息类型 | 提案与动作 | 客户沟通 |
|---|---|---|
| 询问进度或规则 | 保持未完成目标及审批版本；只回答当前事实 | 正在核查、等审批或核验，不能承诺时间 |
| 更正目标 | 先使旧未执行提案失效，再调查新目标，新提案新审批 | 说明已按新范围重新核查 |
| 审批前撤回 | 不再执行，旧批准/迟到批准无效 | 确认未发送部分已取消 |
| 执行中撤回 | 停未发送部分，核验已发送/未知部分 | 不保证已发送能撤回，不称全部未退 |
| 含义不明 | 暂停可能受影响未执行动作并澄清，保留原目标 | 明确需要客户确认的范围 |

命令持久化并按幂等标识消费，不能因重启应用两次。金种子检查正常交互；故意迟到审批和竞态进入 Challenge，并用事件顺序证明触发条件真的发生。

## SOP2-09 退款状态查询

依据：[BIZ2-EVIDENCE-03](BUSINESS_SPEC_V2.md#biz2-evidence-03)、[BIZ2-EVIDENCE-04](BUSINESS_SPEC_V2.md#biz2-evidence-04)。

客户提供付款号则据其核验；没有编号则按相关日期、金额与本人记录定位。所谓唯一记录必须同时满足时间等条件。“上周”按任务业务时钟计算，不使用执行机器今天的时间；申请和完成时间分别对应不同字段。

回复 completed/pending/failed 的真实状态、金额与可用时间；成功空查询只说所查范围未发现记录。既有退款状态查询不触发新退款。客户转述与记录不一致时说明核实结果，不以客户陈述编造退款号，也不指责客户。

## SOP2-10 订阅价格与补偿

依据：[BIZ2-SERVICE-01](BUSINESS_SPEC_V2.md#biz2-service-01)。

核对具体订阅、价格历史、生效时间和政策版本。仅问原因则解释；明确否定补偿不升级。间接要求“这个月从39变49，多的10块能不能补回来”包含订阅补偿请求，应将事实与请求交模拟操作员裁量，不直接给出差额退款提案。

交接保存客户诉求、查证记录、需人工决定的事项和真实交接事件。答复“已交接”必须有事件，“已补偿”必须有资金记录。本轮成功只要求正确交接，不假定人工已批准或退款已到账。没有足够上下文时先调查/澄清，不能从隐藏 case 标签猜业务线。

## SOP2-11 政策与范围外服务

依据：[BIZ2-SERVICE-02 至 04](BUSINESS_SPEC_V2.md#biz2-service-02)。

纯政策按 V2 正文说明，不索要无必要编号。已有退款诉求继续保留，不能只回答一句政策便关闭。

换卡请求使用环境明确提供的模拟菜单“账户设置 → 付款方式”，说明本台不能代改。无需默认转人工，不索取卡号、安全码，不捏造 URL。菜单并非实际网页部署证明；其他渠道没有证据时不编造。

纯他人账户请求明确拒绝并安全结束。没有已定义跨账户人工授权流程，不伪称可以升级后替他人办理。含本人合法事项时继续办理本人的部分。

## SOP2-12 异常交接、结案与质量复核

依据：[BIZ2-EXEC-03](BUSINESS_SPEC_V2.md#biz2-exec-03)及规范第8节。

读取暂时故障至少重试一次安全的等价查询，恢复后继续。持续故障、数据冲突、明确执行拒绝或未知资金结果，向已定义的模拟账务异常操作员交接，附客户范围、必要记录、已发/未发/未知明细、当前批准版本及禁止重做事项。不能将无记录、故障、未知、权限拒绝都归为一个“信息不足”。

结案按用户目标核对：只读查询事实是否完整，全部应退项是否处理，范围外账务是否保持，实际事件是否支持回复。正确不行动不等于失败，安全地什么都不做也不自动等于成功。

复核分别记录结果、必要行为、核心回复、安全事件及未知证据。保留所有失败与安全疑点，抽样成功并保留合法替代路径。记录主因与次因、规则ID、原始证据、修复版本和复测；把新增需求适配、旧规则缺陷修复、题目或评分器修订分开报告。

旧 D02/D06、B0 快照和旧评测不改写。本 SOP 生效为本轮设计依据，但须在可执行任务、政策输入、实现和评分一致后才能运行正式前后对比；没有测量结果时不填简历提升数字。
