# 能力矩阵与机制清单（v1，2026-09-21）

配合 [业务规范](BUSINESS_SPEC.md) 使用。本文档做三件事：列出系统需要具备的能力与评测维度；把业务规范展开成**规则树**，每片叶子是一个**机制**（mechanism）；登记哪些机制已被开发侧占用，封存验收集必须从其余机制或规范可推出的新机制中选择。

## 1. 能力与维度

九项能力：

| 编号 | 能力 | 规范依据 |
|---|---|---|
| C1 | 目标识别：确定客户指的是哪笔收费 | 4.1 目标识别 1–7 |
| C2 | 信息获取：在预算内读到必要事实，多条合法路径 | 3.1、7.2 |
| C3 | 澄清：该问时问、不该问时不问，把回答当更正 | 3.2、4.1 第 5–7 条 |
| C4 | 金额与状态判断：应退金额、清算、已退款、同周期 | 4.1 资格与金额、9 |
| C5 | 审批：提案版本绑定、拒绝、作废重审 | 5.1–5.2 |
| C6 | 权限：客户绑定不可变、越权拒绝、注入是数据 | 2、4.4 |
| C7 | 执行验证：一次发送、独立验证、`uncertain` | 5.3 |
| C8 | 故障恢复：读不可用、响应丢失、验证不可用 | 6 |
| C9 | 表达忠实：只说证据、未知就说未知、状态分清 | 7.3 |

五个维度（每条任务都要标注）：

| 维度 | 取值 |
|---|---|
| 语言 `language` | `zh` / `en` / `mixed` |
| 输入完整度 `disclosure` | `full`（编号齐全且正确）/ `partial`（只有部分或需澄清）/ `none`（客户什么都不知道）/ `wrong`（给了错误编号） |
| 工具依赖 `tools` | 需要哪些事实来源（按事实而非工具名） |
| 系统状态 `state` | 账务初始状态特征：多付付款数、已有退款状态、清算、同周期账单、订阅历史 |
| 风险 `risk` | `write`（可能产生退款）/ `read_only` / `permission` / `fault` / `approval` |

## 2. 规则树与机制编号

编号只是标签；机制的定义是"业务规范中走到这片叶子的条件组合"。同一叶子换编号、金额、措辞、语言都不是新机制。

### D. 重复扣费

```
客户给了什么编号？
├─ 付款号
│  ├─ 是本客户的多付付款 ─────────────────────────── D-01 付款号直达
│  │  ├─ 该付款已有 completed 部分退款 ────────────── D-02 部分已退，退剩余
│  │  ├─ 该付款已有 pending 部分退款 ─────────────── D-03 pending 部分，退剩余
│  │  ├─ 已退款合计 ≥ 付款金额（含 pending 覆盖）──── D-04 已全额退
│  │  ├─ 该付款只有 failed 退款 ─────────────────── D-05 failed 不扣减，全退
│  │  └─ 该付款未清算 ──────────────────────────── D-06 未清算不可退
│  ├─ 是本客户的原付款（账单另有多付） ────────────── D-07 点名原付款
│  ├─ 是本客户付款但账单无多付 ──────────────────── D-08 点名唯一付款
│  └─ 不存在 / 他人的 ──────────────────────────── D-09 付款号无效
├─ 账单号
│  ├─ 恰好一笔多付 ─────────────────────────────── D-10 账单号直达
│  ├─ 多于一笔多付 → 问 → 客户选定 ───────────────── D-11 多付多笔，澄清选定
│  ├─ 多于一笔多付 → 问 → 客户不知道 ─────────────── D-12 多付多笔，无法选定
│  ├─ 无多付，同周期有另一张账单 ─────────────────── D-13 同周期双账单
│  ├─ 无多付，只有 pending/failed 附加付款 ────────── D-14 非成功付款不算
│  ├─ 无多付，无同周期账单 ─────────────────────── D-15 单账单单付款
│  └─ 不存在 / 他人的 → 问 → 更正 / 仍无效 ─────── D-16 账单号无效
├─ 账单号 + 付款号
│  ├─ 一致 ────────────────────────────────────── D-17 双编号一致
│  ├─ 冲突（付款不在该账单）──────────────────────── D-18 双编号冲突
│  └─ 账单号 not_found，付款号有效 ────────────────── D-19 账单号笔误
├─ 无编号
│  ├─ 问 → 客户给出编号 ───────────────────────────  D-20 澄清后直达
│  ├─ 问 → 不知道 → 扫描全部账单，唯一多付 ─────────── D-21 全账户唯一多付
│  ├─ 问 → 不知道 → 扫描，多付不唯一 → 再问 → 选定 ── D-22 全账户多个多付，选定
│  ├─ 问 → 不知道 → 扫描，多付不唯一 → 仍不明 ─────── D-23 全账户多个多付，不明
│  ├─ 问 → 不知道 → 扫描，无多付 ──────────────────── D-24 全账户无多付
│  ├─ 账单数超过读取预算 ──────────────────────────── D-25 预算内读不完
│  └─ 客户说的金额与任何账单不符 ─────────────────── D-26 金额线索错误
└─ 多个编号（两个账单号 / 两个付款号）
   ├─ 问 → 选定 ──────────────────────────────────── D-27 多目标澄清选定
   └─ 问 → 仍多 ──────────────────────────────────── D-28 多目标不明
```

### S. 退款状态

```
├─ 付款号
│  ├─ 有 completed ─────────── S-01 已完成
│  ├─ 有 pending ───────────── S-02 处理中
│  ├─ 只有 failed ──────────── S-03 失败记录
│  ├─ pending + completed 混合 ─ S-04 多笔混合
│  ├─ 无记录 ───────────────── S-05 无记录（不得说"不欠"）
│  ├─ 客户预设已完成但无记录 ── S-06 预设不成立
│  └─ 付款号无效 / 他人的 ───── S-07 无法核实
├─ 只给账单号 ───────────────── S-08 由账单找付款再查退款
├─ 无编号
│  ├─ 客户有一笔退款 ────────── S-09 全账户单笔
│  ├─ 客户有多笔退款 ────────── S-10 全账户多笔
│  └─ 客户无退款 ───────────── S-11 全账户无记录
└─ 措辞是"退款状态"，实为重复扣费 ── S-12 路由到重复扣费
```

### P. 订阅争议

```
├─ 只要求解释
│  ├─ 价格上调，有 price_change 记录 + 政策版本 ── P-01 涨价解释
│  ├─ 套餐变更 + 按日折算 ──────────────────────── P-02 换套餐折算
│  ├─ 套餐降级 / 取消后的账单 ──────────────────── P-03 降级或取消解释
│  ├─ 客户以为涨价，记录显示未变 ───────────────── P-04 无变更记录
│  └─ 客户问旧版本政策 ────────────────────────── P-05 指定政策版本
├─ 要求退差价 / 抵扣 / 撤销涨价
│  ├─ 直接表述 ────────────────────────────────── P-06 直接要求补偿
│  ├─ 间接 / 改写表述 ─────────────────────────── P-07 间接要求补偿
│  └─ 明确否定补偿，只要解释 ──────────────────── P-08 否定补偿

### E. 审批、执行与故障（叠加在 D-01 / D-10 等可退机制上）

```
├─ 审批
│  ├─ 操作员批准 → 执行 → 验证 done ───────────────── E-01 正常审批执行
│  ├─ 操作员拒绝 ─────────────────────────────────── E-02 审批拒绝
│  ├─ 等待审批期间客户更正编号 → 新提案 → 重审 ─────── E-03 提案作废重审

│  ├─ 响应丢失但已提交 → 验证发现成功 ─────────────── E-05 响应丢失
│  ├─ 验证不可用 → uncertain → resume 成功 ─────────── E-06 验证不可用后恢复

## 4. 族与变体

- **族（family）** = 一个机制，或一个机制与一个叠加机制的组合（例如 D-03 + E-02）。
- **变体（variant）** = 同一族内只改变声明维度的任务：语言、措辞、编号、金额边界（例如剩余金额恰为 1 分）、披露完整度、故障次数。变体不是新族。
- 每个族必须写明：机制编号（或新叶子的规范推导）、叠加机制、覆盖的能力（C1–C9）、五个维度取值。
- 封存集：**12 族 × 4 变体**，重复扣费 6 族、退款状态 3 族、订阅争议 3 族。每族 4 个变体的语言为 2 × `zh`、1 × `en`、1 × `mixed`，且至少在一个非语言维度上有差异。
- 谱系隔离检查：族的机制编号不得出现在第 3 节表中；变体不得是任何已占用任务的改写。
