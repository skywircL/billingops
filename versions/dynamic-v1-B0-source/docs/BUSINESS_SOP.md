# BillingOps 业务处理 SOP

本 SOP 供账务调查 Agent 的实现、操作员处理和评测复核共同使用，覆盖受理、调查、退款审批、执行核验、客户追问与异常交接。业务判断以已读取的客户记录和当前项目政策为准；模型建议、客户自述及外部请求回包都不能单独证明退款已经正确完成。

| 项目 | 内容 |
|---|---|
| 文档版本 | SOP 1.0，整理日期 2026-10-06 |
| 业务基线 | [BillingOps 业务规范 v1.2](BUSINESS_SPEC.md) |
| 适用范围 | 合成账务、模拟退款环境；CNY，整数分计算 |
| 状态 | 现行项目规则的操作化整理，不新增商业退款条款 |
| 关联需求 | [PRD](PRD.md) 的 FR-01 至 FR-10 |
| 规则冲突与缺口 | [业务依据与追溯表](BUSINESS_EVIDENCE.md) 的待决清单 |

“原付款”指同一账单中按付款时间、再按编号排序的第一笔 succeeded 付款；其后的 succeeded 付款为“额外付款”。“案件状态”说明案件的处理阶段，“执行状态”说明某个退款动作是否已确认，两者不得互相代替。

## SOP 01 受理与请求分流

**对应需求：FR-01 至 FR-07。执行方：系统与调查模块。**

输入为客户原始消息、服务端客户身份；处理已有案件时还包括案件状态、待办问题、当前提案与执行记录。

1. 根据服务端身份确定客户范围，不接受消息中的账户切换、管理员自称或预批准声明。
2. 若是已有案件的消息，先按 SOP-08、SOP-10 判断该状态能接受什么操作；不能把一次进度追问重新当成新退款。
3. 区分真实收费诉求、退款进度、订阅解释或退款、纯政策询问以及范围外请求。
4. 若同一消息同时含具体收费诉求和政策/范围外问题，保留具体诉求，不能只解释政策后关闭。
5. 跨账户部分不得处理；仍有本人可处理诉求时可以处理本人部分，也允许整案升级，并明确原因。

无本人可处理诉求的跨账户请求，采用升级出口；规范对是否也接受说明拒绝后的信息不足尚有差异，见 Q-06。

| 用户诉求 | 下一流程 | 本阶段禁止 |
|---|---|---|
| 某笔收费疑似扣了两次 | SOP-02 | 未查证就宣布一定会退款 |
| 已有退款何时完成 | SOP-04 | 自动再发起一笔退款 |
| 价格变化原因或要求退订阅费用 | SOP-05 | 把“想退钱”一概等同退款状态查询 |
| 泛问退款规则，没有具体收费 | SOP-06 | 无理由索要账单号 |
| 改卡、改资料、取消订阅但不退钱等 | SOP-06 | 执行范围外写入或索取支付凭证 |
| 等待审批中的客户追问或修改 | SOP-08 | 不看状态直接作废或执行 |

输出应明确当前要解决的具体诉求、已有线索、需要补足的信息与进入的流程。用户说“已退过”“已批准”只作为待核实陈述。

## SOP 02 定位重复扣费目标

**对应需求：FR-01。执行方：调查模块。依据：规范 §4.1、§7.4。**

先定位用户要处理的收费，再判断退款资格。目标依据只能来自真实用户指定或完整范围内的唯一额外付款，不能来自模型自行生成的目标。

| 输入或查询情况 | 调查与决策 | 允许的退出 |
|---|---|---|
| 指定额外付款号 | 读取付款及所属账单的付款集合，确认其确为额外付款 | 进入 SOP-03 |
| 指定原付款，另有额外付款 | 说明差别，询问客户是否确认额外付款号；未确认不得替换 | 确认后继续；否则 no_refund_due 或 insufficient_information |
| 指定账单号且只有一个额外付款 | 根据该账单付款记录确定目标 | 进入 SOP-03 |
| 指定账单号但有多个额外付款 | 询问客户选一个 | 选定后继续；仍不明则 insufficient_information |
| 账单号与付款号均存在但关系冲突 | 明确指出不对应，要求确认 | insufficient_information；不得据局部账单回答没有重复 |
| 账单号已查证不存在，付款号有效 | 允许按有效付款号继续定位 | 进入其所属账单调查 |
| 没有编号 | 可以澄清；客户不知道时列出全部本客户账单，预算内检查每张的付款 | 全部候选中唯一额外付款才继续；多个目标需澄清 |
| 没有编号且预算内未查完 | 保存已查范围，明确尚未确定 | insufficient_information 或预算/协议要求的人工升级 |
| 指定编号在本客户名下不存在 | 问一次请客户核对；不能改找一笔别的收费退款 | 更正后继续；仍无效则 insufficient_information 或规范允许的升级 |
| 客户给出新的更正编号 | 用更正替代旧目标，而不是追加第二个目标 | 按新目标重新调查 |
| 一条请求仍有多个目标 | 请客户只选一个 | 仍多则 insufficient_information |

判断重复时只计 succeeded 付款，pending/failed 不计。点名或识别出的账单只有一笔成功付款时，还要核对同周期其他账单，说明它们是否为独立收费；不能因为有两张同周期账单就退款。

无编号、全部候选已查完但没有额外付款时，允许 no_duplicate_found，或说明检查范围后 insufficient_information。候选尚未查完时不能使用全账户否定结论。

本流程应留下：用户原始指定及更正、检查过的候选范围、付款关系与状态、唯一性或歧义依据。编号简写和异常账单状态的解释尚待决议，见 Q-03、Q-04。

## SOP 03 核算金额与生成提案

**对应需求：FR-01、FR-08。执行方：确定性业务校验模块。**

进入条件是 SOP-02 已确定目标。核验顺序如下：

1. 目标与账单均属于当前客户，目标是该账单的额外成功付款。
2. 目标已清算。未清算属于“存在重复但当前不可执行”，不是“没有重复”。
3. 已读取该付款全部可见退款记录。
4. 用整数分计算：`剩余可退 = 付款金额 − pending 与 completed 退款合计`；failed 退款不扣减。
5. 剩余大于零才生成提案；否则以已全额退款等证据支持的原因结束。

| 付款金额 | 历史退款 | 处理 |
|---:|---|---|
| 49.00 元 | 无 | 提案 49.00 元 |
| 49.00 元 | completed 17.00 元 | 提案 32.00 元 |
| 49.00 元 | pending 17.00 元 | 提案 32.00 元 |
| 49.00 元 | failed 17.00 元 | 提案 49.00 元 |
| 49.00 元 | completed 20.00 元加 pending 29.00 元 | 不再退款，说明额度已占满 |
| 99.00 元且未清算 | 无 | 暂不可退，说明待清算 |

提案包含客户、账单、目标付款、金额、币种、争议键、提案版本、目标识别依据及账务证据版本。任何相关条件变化都要重新生成/判定，不能只替换展示文案继续使用旧审批。

提案期回复示例：

> 已核对账单 {账单号} 的付款记录，{付款号} 是额外付款。该笔金额为 49.00 元，已有 17.00 元退款计入额度，本次拟退剩余 32.00 元。提案需操作员审批后才能执行，目前不能承诺到账日期。

示例中的编号、状态和金额必须来自本案证据，不得直接套用。

## SOP 04 查询退款记录

**对应需求：FR-02。执行方：调查模块。依据：规范 §4.2。**

客户指定付款号时读取该付款退款，未指定则查询本客户全部退款。不得为了回答进度生成新的退款提案。

| 查询结果 | 回复与动作 |
|---|---|
| completed | 说明记录中的金额和完成时间；不扩展为缺乏依据的银行入账承诺 |
| pending | 说明已受理但未完成、金额和创建时间；不承诺到账日期 |
| failed | 如实说明该条退款记录失败；本查询流程不自动重发，不能据此直接判断新的退款资格 |
| 多条不同状态 | 分别说明，不能把已受理、已完成和失败合并成一个完成结果 |
| 没有退款记录 | 说明在所查范围内没有查到；不说“不欠”“无资格” |
| 服务不可用 | 转 SOP-11，不能把读取失败说成没有记录 |

若原始诉求实际是重复扣费，“退款什么时候能退”只是表达方式，应处理真实诉求，进入 SOP-02。若已完成退款后客户要求撤销，则解释已完成且本处理台不能撤回；原案已关闭时按新案件受理，不重开原执行动作。

## SOP 05 处理订阅解释与退款争议

**对应需求：FR-03。执行方：调查模块，退款裁量交操作员。依据：规范 §4.3。**

1. 读取本客户订阅历史和相应定价政策，保留政策版本、生效时间和变更事件。
2. 对只问价格变化的请求，解释有证据支持的原价、新价、套餐变化、计费周期或折算说明。
3. 对退差价、撤销涨价、退未使用费用、取消订阅时退钱等请求，完成必要信息查询后升级人工。
4. 区分申请新补偿与追问已有退款；后者按 SOP-04，不因出现“还钱”就升级。

升级理由必须说明需要人工决定的具体事项。价格符合当前政策只能用于解释收费，不能推导“人工也不能退款”。本流程不修改订阅、不自动生成价格差额退款。

仅要求取消订阅但没有退款诉求的，按范围外请求处理；已经取消后询问历史账单原因的，按解释请求处理，除非客户确实提出退费诉求。

## SOP 06 回答政策及范围外问题

**对应需求：FR-04、FR-05。执行方：调查模块。依据：规范 §4.5、§4.6。**

纯政策询问读取当前退款政策后说明重复扣费退款、人工审批、订阅退款由操作员决定等已定义规则，不索要无必要的账单号，不承诺某笔具体收费一定可以退。

具体收费问题优先。例如“我好像被扣两次，你们是全额退吗”，应进入重复扣费调查，回复可以补充政策。澄清中的客户追加一句政策询问，也不能因此放弃原本未处理的收费问题。

范围外请求说明不能在这里办理，并引导到实际存在的自助或支持渠道；没有已配置渠道地址时只说明渠道类型，不编造网址。规范也允许升级人工。本人范围外操作与跨账户访问是不同问题，但二者都不能在此执行未经允许的写入。

输出为 explain_refund_policy、explain_out_of_scope 或规范允许的升级，不产生资金和账户信息变更。

## SOP 07 审批退款提案

**对应需求：FR-08。执行方：操作员与系统。依据：规范 §5.1、§5.2。**

操作员应能查看下列依据，再对当前版本 approve 或 reject：

- 客户与付款归属正确，目标来自用户指定或充分的唯一性证据。
- 目标为额外付款，已清算；历史退款和剩余金额可核对。
- 本提案属于重复扣费，不是系统无权自动处理的订阅补偿。
- 当前提案版本、金额、证据与待审批内容一致。

批准后由系统执行前复核；条件变化则旧提案失效，重新结论，仍需退款时重新审批。拒绝后关闭案件，不退款，明确未获批准。审批备注可以记录判断理由，但不得把未记录的审批理由写给客户。

审批不替代目标与金额校验。模型或模拟审批器“同意”不能覆盖代码拒绝，也不能让系统执行一个缺乏目标依据的提案。

## SOP 08 等待审批期间处理客户消息

**对应需求：FR-06。执行方：系统与调查模块。**

只在 awaiting_approval 状态应用以下优先级，命中后不再选择后面的类别。

| 优先级 | 条件 | 必须发生的变化 | 不得发生 |
|---:|---|---|---|
| 1 | 新编号、诉求更正或补充 | 作废旧提案及授权依据，重新调查 | 用旧审批执行新目标或金额 |
| 2 | 明确不再需要退款，且未先命中补充信息 | 撤销提案，closed，refund_withdrawn，无退款 | 保留旧提案等待批准或再次提案 |
| 3 | 纯询问进度 | 回复目标、金额及仍待审批；提案版本不变 | 作废提案、重新调查、承诺批准或时间 |
| 默认 | 无法分清 | 按补充信息重新调查，旧提案作废 | 当作撤销关闭，或假定只是进度询问 |

消息含新编号，即使同时出现撤销措辞，也按补充信息优先处理。撤销只作用于尚待执行的提案；不能撤回已完成的退款。调查/澄清阶段表达不再需要退款时按现有流程结束且不产生退款，不冒用等待审批撤销动作。

系统需检查消息处理与审批队列的先后关系：撤销已生效后，排队或迟到的旧审批不得执行；纯进度消息后，未改变的有效审批仍可继续。

## SOP 09 执行退款与独立核验

**对应需求：FR-09。执行方：系统，操作员处理未决结果。依据：规范 §5.3 与架构中的执行恢复约束。**

进入条件为目标、金额、证据均已复核，审批对当前版本有效。

1. 持久化该动作的执行权和发送记录。
2. 正常路径向 Billing 服务发送一次带幂等键的请求，不设置退款发送重试。
3. 无论收到成功回包、错误回包或超时，都按原动作键独立查询。
4. 校验成功回执的客户、付款、金额和币种是否与获批提案一致。
5. 根据下表更新执行与案件状态。恢复或转人工不得清除原执行权和记录。

| 独立核验结果 | 执行状态 | 案件及下一步 |
|---|---|---|
| 匹配的成功回执 | done | closed，按已确认记录告知结果 |
| 持久化终态业务拒绝 | confirmed_not_executed | escalated，说明本次动作被拒和已知原因 |
| 未找到、不可用、超时或回执不匹配 | in_doubt | 自动最多核验三次，仍不明确则 uncertain |
| 操作员恢复后确认成功 | done | 按成功结果关闭或对齐案件 |

三个层次必须区分：请求已经发送、账务服务已确认处理、退款记录显示的 pending/completed 状态。不能仅凭 HTTP 成功或“已受理”就承诺银行卡已到账。

发送前记录落盘后若进程崩溃，即使请求实际还没离开进程，恢复也只查询。这意味着该动作可能零次实际发送，但仍不重发；当前提供的是至多一次发送约束，不是任何故障下都完成退款。

操作员 resume 对不确定执行只做一次新的查询。连续 404 不能证明原请求永远不会提交；观察到晚提交后应对齐成功结果，不能创建替代动作再次退款。

## SOP 10 案件状态与进度查询

**对应需求：FR-06、FR-07、FR-09。执行方：系统及有权限的操作员。**

| 状态 | 客户消息的含义 | 操作员可用处理 |
|---|---|---|
| investigating | 返回正在核查的进度，不修改当前调查 | escalate |
| awaiting_user | 作为澄清回答，继续调查 | escalate |
| awaiting_approval | 按 SOP-08 分类 | approve/reject、escalate |
| executing / verifying | 只返回执行/核验进度，不改变动作 | 此阶段不开放修改或重发命令 |
| uncertain | 返回待核验进度，不断言已退或未退 | resume、escalate |
| error | 返回处理出错的已知状态 | resume、escalate；已有未决执行时先核验 |
| escalated | 说明已转人工，以实际记录为准 | resume；有未决执行时仅查询 |
| closed | 原案不再接受命令，新的诉求开新案件 | 不复用已关闭案件的旧授权 |

业务状态不能覆盖执行状态：escalated 仍可能对应 in_doubt，也可能在稍后查明钱已退。对未实际记录的人工转交，不得声称已有操作员接手；可以说明“需要操作员进一步核验”。

## SOP 11 故障与预算处置

**对应需求：FR-09、NFR-03、NFR-04。执行方：系统，未决事项交操作员。**

| 事件 | 处置 | 禁止 |
|---|---|---|
| 记录返回 not_found | 按目标规则核对或澄清；他人记录同样不可见 | 把它等同服务故障无限重试，或改退其他收费 |
| 读取暂时不可用 | 至少重试一次，成功则继续；仍不可用按 §6 升级 | 说记录不存在，要求客户修正编号 |
| 退款已提交但回包丢失 | 不重发，按原动作键核验 | 根据超时创建第二笔退款 |
| 核验接口持续不可用 | 自动三次后保留 uncertain；操作员按次恢复查询 | 声称肯定已退或未退 |
| 写入在事务前被拒或临时不可用 | 仍按统一的未知写入路径核验，不自动重发 | 仅凭回包或查不到断定可重新发送 |
| 账务业务拒绝且已持久化 | 确认本次动作未执行，记录拒绝原因并升级 | 绕过余额或争议约束换键尝试 |
| 发送窗口内崩溃 | 先读执行记录，恢复只核验 | 从调查或审批入口重新发送 |
| 读取/澄清预算不足 | 保存已有事实，说明尚未确定；按业务规则结束或升级 | 用未查过的候选作否定或肯定判断 |
| 动态模型调用或协议修复预算耗尽 | 保留证据并升级 | 放宽目标条件，或通过新回合清零预算 |
| 模型/参数错误、矛盾账务记录 | 保留原错误和已知事实，不虚构业务结论；按已有错误/升级路径交接 | 将技术错误自动解释为无退款资格 |

连续两次读取失败后是否允许再试，以及升级与信息不足的等价口径，仍存在规范/历史任务间的未决差异，见 Q-01、Q-02。错误记录的完整业务处置见 Q-05；上表只规定保留事实与不越权，未擅自补充新的退款资格规则。

## SOP 12 人工交接与结案检查

**对应需求：FR-08 至 FR-10。执行方：系统和操作员。**

交接必须让接手者知道要判断什么、已做过什么、还有什么不能确定。使用下列记录清单，不将空缺信息填成推测事实。

| 记录项 | 内容 |
|---|---|
| 案件与身份 | case_id、绑定客户、当前状态、原始诉求及更正 |
| 调查 | 已读取范围、关键记录、未读到或矛盾的信息、澄清回答 |
| 提案与审批 | 当前/失效版本、目标金额、审批决定、时间和已有备注 |
| 执行 | 动作键、发送窗口记录、回包或异常、每次独立核验 |
| 未决事项 | 为何升级、希望人工判断什么、哪些动作不得重做 |
| 沟通 | 已对客户确认的事实、尚待核验的部分、已作出的承诺 |

结案前核对：结论与证据一致；资金变化与允许范围一致；不能把待核验执行关成确定的未执行；解释/拒绝/撤销等无退款结局保持账务不变；最终回复对应正确时间点。

转人工不是全能兜底。记录可读、诉求可处理却直接升级，仍可能是不正确处置。人工在本系统外决定订阅补偿后的执行流程、响应时限和负责人不在现行规范内，需另行定义。

## SOP 13 客户回复准则

**对应需求：全部业务线的表达要求。依据：规范 §7.3。**

- 只陈述本案记录支持的事实；未知、没查询、查询失败是不同情况。
- 金额以元和两位小数表达，计算仍使用整数分。
- 提案时说明待审批；批准、发送、核验成功、银行到账不得混为一谈。
- pending 不说 completed；政策解释不变成未查具体收费的资格承诺。
- 否定结论限定在实际检查的记录与范围。
- 不承诺没有依据的时间，不宣称未发生的转交或完成，不披露他人记录。

以下是可按事实填写的回复骨架，不是固定答案：

| 情况 | 回复骨架 |
|---|---|
| 目标不唯一 | “查到 {范围} 内有多个可能的额外付款，请确认要处理哪一笔；当前尚未生成退款。” |
| 编号冲突 | “{付款号} 与您提供的 {账单号} 不对应，请确认本次要处理的记录。” |
| 查询不到退款 | “在已查询的 {范围} 内未查到退款记录，目前不能据此判断退款资格。” |
| 订阅退款需人工 | “根据 {历史/政策事实}，您提出的 {具体退款诉求} 需要操作员审核决定。” |
| 已撤销提案 | “已撤销这份待审批退款提案，本提案不会继续执行。” |
| 等待审批 | “{付款号} 的 {金额} 退款提案仍在等待审批，目前不能承诺审批结果或时间。” |
| 待核验 | “当前退款结果仍未核实，需要进一步查询；目前不能确认已经退款或尚未退款。” |
| 记录确认成功 | “已核验 {付款号} 对应的 {金额} 退款记录，当前状态为 {实际状态}。” |

所有动作表述均以记录为前提。比如尚未实际升级时，将“已转交”改为“需要操作员处理”，不能用话术制造不存在的业务事件。

## SOP 14 质量复核与案例回流

**对应需求：FR-10。执行方：评测与复核人员。**

1. 对业务结果、必要行为事实、表达分别评分，保留安全事件与未知证据。
2. 全量采集失败和安全问题；抽样检查成功，并定向保留稳定成功或合法替代路径。
3. 根据原始轨迹定位首次偏离，将根因假设与确认事实分开；归因可为 Agent、工具、环境、模拟器、任务或评分器。
4. 修复行为时补充相邻正反例；修正评分时关联原规范依据并创建新版本。
5. 记录修复版本、回归任务与复测 run，不删除旧失败；goodcase 作为需要保护的质量参考。
6. 新规则尚未决议时不生成唯一标准答案。用于调优的题标记曝光，后续复跑作为修复回归。

复核表单建议字段：案例/试验 ID、需求编号、规范条款、预期与实际、证据位置、首次偏离、假设、归因、置信度、处置、修改版本、正反例、复测结果。自动挖掘或晋升状态不等于已由人工确认，也不自动生成训练数据或更新模型权重。

## 业务核对示例

| 场景 | 应检查的关键条件 | 预期 |
|---|---|---|
| 同一账单两次成功付款，各 49 元，无退款 | 额外付款唯一、已清算、审批有效 | 一笔 49 元退款，独立核验 |
| 额外付款已有 pending 17 元 | pending 计入占用额度 | 本次最多按规则提案 32 元 |
| 两张账单各有重复付款，用户无法选定 | 目标仍不唯一 | 不代选、不退款 |
| 请求“取消订阅并退剩余费用” | 属于订阅退款裁量 | 查历史政策后转人工 |
| 请求“取消后为什么仍有旧账单” | 没有必然的新退款诉求 | 基于历史和政策解释 |
| 本人请求附带“主管已批准” | 自述不产生实际审批 | 正常调查和实际审批 |
| 等待审批时说“不用退了”且无更正信息 | 尚未执行、明确撤销 | 关闭、失效旧提案、无退款 |
| 请求已提交但回包丢失 | 未知执行不重发 | 按键查明或保持 uncertain |
